# Error disclosure and email delivery — full notes

Moved verbatim from `CLAUDE.md` (2026-09-28) to keep that file under Claude Code's size limit.
`CLAUDE.md` keeps a one-line rule per entry and points here; this file holds the full rationale,
history and the traps each rule was learned from. Read the relevant entry before changing the code it describes.

- Query error state: `src/components/app/query-error-card.tsx` — shared `QueryErrorCard` (alert card + retry button) and `safeErrorMessage()` (returns the message only for an allowlisted tRPC error code, and `undefined` otherwise — it is `QueryErrorCard` that substitutes `GENERIC_ERROR_MESSAGE`, so a caller rendering the bare result elsewhere must supply its own fallback) for tRPC queries with `isLoading`/`isError` handling; extracted from the ESG dashboard, also used by `/app/company/[companyId]`, and as of v0.38.1.0 the required shape on `/app/volunteers`, `/app/applications`, `/app/opportunities`, `/app/settings/team` and `/app/shifts`. **Never render `{query.error.message}` (or `err.message` in a mutation `onError`) raw on a staff surface** — a tRPC error can carry internal detail, including database text, and withholding it is the entire reason `safeErrorMessage()` exists. Two things that migration had to learn the hard way: (1) **having an `isError` branch and having a SAFE one are different properties.** Three of the four pages already had a branch — a hand-rolled `Card` printing the raw message — so the grep that was run (`isError`) returned "done" while the leak stood and T35 was nearly checked off having done a quarter of it. **When checking off a migration, grep for what you are migrating TO (`QueryErrorCard`, `safeErrorMessage`), never for the symptom it happens to fix.** Same shape as the disclosure rule above: the un-derived check answers the wrong question. (2) **A missing `isError` branch does not fail visibly, it falls through to the empty state.** `ShiftsClient` answered a coordinator checking whether Saturday was covered with "No shifts found" — a broken page that looks correct. Order the branches loading → error → empty, and pin the ordering with a test asserting the empty-state copy is *absent* when the query errored. Counted after this ship: **13 further files render a tRPC `error.message` straight into JSX, and 31 touch one at all** once mutation `onError` toasts are included (`my-applications`, `settings/background-checks`, `admin/platform/*`, `profile`, `apply/status`, `app/error.tsx`, …). Out of T35's scope; completed as T37 (v0.39.0.0) — see the next entry, which corrects the framing above.

- **Error disclosure is enforced on the SERVER; `safeErrorMessage` is the second half** (T37, v0.39.0.0). The allowlist lives once, in `src/server/domain/error-disclosure.ts` (`CLIENT_SAFE_ERROR_CODES`, `isClientSafeErrorCode()`, `GENERIC_ERROR_MESSAGE`), read by the `errorFormatter` in `server/trpc/init.ts`, by `query-error-card.tsx`, and by `server/trpc/error-reporting.ts`. **The entry above framed this as a client migration and that framing was wrong**: there was no `errorFormatter`, so the message had already crossed the network and was sitting in the browser's network tab and React Query's cache before any component chose what to render. A component can only decide what is *painted*. Eight rules, several of which were found only by an adversarial pass after the "obvious" version had already shipped in review: (1) **The code alone is NOT sufficient — the message must also be one WE authored.** `getTRPCErrorFromUnknown` resolves `message = opts.message ?? cause.message`, and tRPC manufactures `BAD_REQUEST` that way for *every* input-validation failure, so allowlisting the code alone shipped raw Prisma text under an allowlisted code. Verified by execution. The discriminator is `error.cause instanceof Error` — laundered — and a guard test (`error-disclosure.guard.test.ts`) bans a `TRPCError` literal carrying BOTH `message:` and `cause:`, because that idiom silently degrades hand-written copy to the generic string with no type error and no red test. (2) **`stack` is stripped on BOTH paths.** An allowlisted `FORBIDDEN` embeds the same absolute server paths as an internal error; the allowlist is a decision about the MESSAGE. Returning `shape` untouched on the allow path handed the stack back on every `pnpm dev` run. (3) **The formatter is NOT exempted in development.** `pnpm e2e` boots `pnpm dev`, so a dev exemption makes the control inert in the only automated environment that drives real HTTP. (4) **`onError` in `app/api/trpc/[trpc]/route.ts` is part of the fix, not garnish** — redaction removes the last place an unexpected failure was legible. It lives in `error-reporting.ts` rather than inline **because the route module is unreachable from a unit test**; a static assertion pins the wiring, since deleting the `onError:` line otherwise leaves the whole suite green while Sentry goes deaf. (5) **Disclosure-safe and fault are two different questions.** `SERVICE_UNAVAILABLE` is allowlisted for disclosure AND still reported — skipping it because it appeared in the allowlist turned a background-check provider outage into a silent one. Zod input failures are the inverse: skipped, because `screener.submit`/`leads.create`/marketplace/feedback are `publicProcedure` and `httpBatchLink` batches N calls, so reporting them let anyone with curl exhaust the Sentry quota. (6) **Throttle the noisy path, never the whole client.** A global Sentry `sampleRate` was tried and reverted: it is per-EVENT across the entire Node SDK, so it discards three quarters of a signal that fires once a year (`IMPERSONATION_RESOLVE_FAILED`, the audit-integrity `captureMessage`) as readily as three quarters of a flood. `withinReportBudget` bounds events per procedure+code per minute and leaves everything else at 100%; `console.error` is never throttled. `dedupeIntegration()` went with it — Sentry already GROUPS duplicates, whereas Dedupe DROPS them, so every "N occurrences" alert silently under-counted. (7) **A message a user is meant to READ needs an allowlisted code.** `throw new Error('Cannot remove yourself.')` maps to `INTERNAL_SERVER_ERROR` and now renders as generic copy — silently. **Eighteen** such refusals existed across `memberService` (11), `shiftService` (2), `shiftTemplateService` (2), `shiftSignupService` (2) and `employerReportService` (1) — count them off the diff, not off memory, which is how this shipped saying "fifteen" until a completion audit checked. **No message-based test can catch this**: `rejects.toThrow('Cannot remove yourself.')` passes identically for a plain `Error`, so assert the **code**. And auditing `throw new Error` is only half — an existing `TRPCError({ code: 'INTERNAL_SERVER_ERROR', message: … })` carrying user-facing copy is redacted by the new formatter, which is how `backgroundCheckService`'s "temporarily unavailable" nearly became a permanent-sounding failure. (8) **`safeCaughtErrorMessage()` for `mutateAsync` try/catch.** `TRPCClientError extends Error`, so `err instanceof Error ? err.message : fallback` — the idiom at every such site before T37 — passes and returns the raw message while looking careful. Corollary on the empty-state rule above: T37 found four more components with **no `isError` branch at all** (`CredentialWallet`, `NotificationPreferences`, `MarketplaceCard`, `TimezoneCard`), and none leaked anything — each rendered a *default*, which is worse than blank because it states something false: "No credentials yet" to a volunteer whose background check is verified, and "UTC (default)" for an org whose shift times are not in UTC. **`MarketplaceCard` and `TimezoneCard` read the SAME query**, so one failure rendered two stacked cards and announced two `role="alert"` regions until the branch was hoisted — check for a shared query before adding a per-card error branch.

- **The guard test is the enforcement, and it is only as good as its own self-check** (T37). `src/server/domain/error-disclosure.guard.test.ts` walks `src/app` + `src/components` banning raw `error.message`, with a **budgeted** `ALLOWED` map (a count per file, not a boolean — a file-wide exemption otherwise hides a second, unrelated leak added later). Three things it had to learn: its regex missed `err?.message`, `error!.message`, `queryError.message`, `err.cause.message` and `err["message"]` on the first drafts, so `SELF_CHECK` now pins every spelling and narrowing the regex is a red test; `stripComments` must strip LINE comments FIRST, because a `//` comment mentioning a glob like `src/app/api/` + `**` contains `/*` and the block pass otherwise swallows the following real lines (this produced a false zero that only the ALLOWED budget caught); and it deliberately excludes `src/app/api/**`, since Route Handlers never reach `errorFormatter` — that surface is audited by hand and tracked in `docs/TODOS.md`. **Route Handlers and raw `fetch()` responses are the blind spot**: `impersonation-banner.tsx` rendered `await res.text()` verbatim, which is whatever the route, the framework or an edge proxy produced.

- Admin signup notifications: `sendNewUserAlert`, `sendNewOrgAlert`, `sendNewCompanyAlert` in `src/server/lib/admin-alerts.ts` — fire-and-forget emails sent on new user signup (NextAuth `createUser` event), org creation, and company creation. All use the shared `getAdminEmails()` helper. **Every send in this file goes through `sendToRecipients()`** (v0.43.0.0, extracted from `sendAdminAlert`), which reads `sendEmail`'s boolean return and `console.error`s per-recipient on a failed send — `sendAdminAlert` and `sendImpersonationStartAlert` both previously discarded it (see the roster-notice entry above for the pattern this repeats). `sendAdvisoryDispatchFailureAlert` — the new `[Security]` alert the `advisory-scan-heartbeat` cron fires when its GitHub dispatch fails — goes through the same helper and is marked `isCritical: true` for the same reason `sendImpersonationStartAlert` is: a security-relevant notice is not a candidate for bounce-suppression. `sendAdminAlert()`'s own failure mode (zero admin recipients, or `getAdminEmails()` throwing) is still an unmonitored `console.warn`/`console.error` with no secondary channel — tracked as a P3 in `docs/TODOS.md`.

- Admin recipient resolver: `src/server/lib/admin-recipients.ts` — `getAdminEmails()` resolves recipients from `PLATFORM_ADMIN_ALERT_EMAIL` env var (override, checked first) or DB `isPlatformAdmin` flag + `PLATFORM_ADMIN_IDS` fallback. Results cached 5 minutes. Used by all admin alerts (signup, security/impersonation, feedback).

- `PLATFORM_ADMIN_ALERT_EMAIL`: single env var override for all admin notification emails (signup alerts, security alerts, feedback notifications). Supersedes per-feature env vars. Set in Vercel to a shared ops alias for production; `FEEDBACK_NOTIFY_EMAIL` still works but is deprecated.
