# Background checks and credential expiry — full notes

Moved verbatim from `CLAUDE.md` (2026-09-28) to keep that file under Claude Code's size limit.
`CLAUDE.md` keeps a one-line rule per entry and points here; this file holds the full rationale,
history and the traps each rule was learned from. Read the relevant entry before changing the code it describes.

- **A background check is DISCLOSED to its subject, and that email is the control** (v0.40.0.0). `backgroundChecks.initiate` is gated only by `requireOrgVolunteerRelationship`, which accepts `ORG_VOLUNTEER` — a roster row staff mint from an email address alone, sixty at a time via `pnpm import:roster`. So the platform could make a paid third-party call carrying someone's SSN and date of birth with no record they had agreed and **no way for them to find out**: the only background-check email went to org STAFF on a CONSIDER result, and the volunteer heard from us only on the FCRA pre-adverse path, i.e. only if the report came back badly AND the coordinator acted on it. Tiering `ORG_VOLUNTEER` out of the accepted set for this action was considered and **rejected** — the coordinator must already hold the SSN and DOB to submit the form, so an in-app edge adds no consent that is not already there, while blocking the concierge case outright (a spreadsheet of existing volunteers is entirely people who have never logged in). The subject is the only party who CAN detect an unauthorized check, so the fix is disclosure. Six rules, most of which were bugs first: (1) **The recipient is resolved from `userId` via `findEmailByUserId`, NEVER from `pii.email`** — that block is staff-supplied free text, so sending there hands the subject's only disclosure back to whoever is running the check. Same rule as `ctx.session.user.email` not being the effective user's address. Mutation-verified. (2) **`waitUntil`, not a bare `void`.** On Vercel the function can be frozen as soon as the tRPC response is written, so a floating promise races the freeze — and the thing dropped is the only disclosure the subject ever receives. `bulk-import-service.ts:98` already established this; the `.catch` stays INSIDE, because `waitUntil` keeps the instance alive but does not handle rejections. A test asserts `waitUntil` was called with a Promise, or "simplifying" it back to `void` is invisible to the whole suite and breaks in production only. (3) **`sendEmail` RETURNS `false` and never throws** — for a Resend error and for a bounce-suppressed address — so a `.catch` never fires on the likeliest failure. The boolean is read and a lost notice logs `DISCLOSURE NOT SENT` via `console.error`. **Two tests are needed, returns-false and rejects**: the rejection test passed while the returns-false hole stood. (4) **NOT `suppressUnclaimed`.** The guard is opt-in so the default is already right, but that is load-bearing rather than incidental: a volunteer typed in from a spreadsheet who has never logged in is exactly the person with the weakest consent and the strongest claim to be told. (5) **Guard 0 — the FCRA attestation — is refused in the SERVICE, not as `z.literal(true)` on the router**, because a Zod failure arrives as a tRPC-manufactured `BAD_REQUEST` whose message comes from the cause, which `errorFormatter` redacts to generic copy; the coordinator would be refused with no way to learn why. It runs BEFORE any query, so an unattested request never touches the volunteer's row. (6) **`consentAttestedBy` is evidence, so it is a plain `String` with no FK** (`AuditLog.actorId`'s `ON DELETE SET NULL` would empty it when the coordinator leaves — worthless in exactly the dispute it exists for), it is **not backfilled** (NULL means "we do not know", and inventing a value manufactures evidence about a real person's consent), and the audit row stamps `impersonatedBy` — `createTRPCContext` rewrites `session.user.id` to the impersonated target, so without it a platform admin can produce evidence falsely naming a coordinator as having sworn they hold a signed authorization. The gap this left — nothing bound the submitted `pii` to the `userId` — was closed by Guard 1.5 in the next entry.

- **The submitted PII must describe the volunteer being checked, and the email is the only field that can prove it** (T38, v0.41.0.0). `initiate` takes a `userId` AND a free-text `pii` block from the same form; until Guard 1.5 nothing checked they were the same person, so picking the wrong row sent a STRANGER's SSN and date of birth to a consumer reporting agency, filed the report against the intended volunteer, and stamped `consentAttestedBy` with a coordinator's name for a report about a different human. Guard 1.5 lives in `initiateProviderCheck` — the shared path, so both provider entry points inherit it, exactly as Guard 1 does. Five rules: (1) **The email is a CONFIRMATION field, not a payload field.** It must equal the account address (`normalizeEmail` on BOTH sides, plain equality — never `mode: 'insensitive'`), and what reaches the provider is the ACCOUNT's address regardless of what was typed. So the coordinator-controlled field can only confirm the identity, never steer the provider's correspondence. (2) **Deleting the field instead was considered and REJECTED** — it is strictly weaker. Deriving the address means the identity is never restated, so the wrong-row case proceeds in silence; requiring a match is what converts a row mistake into a refusal. This is the one place the "delete the parameter rather than validate it" rule (v0.34.0.0) does NOT apply, because here the redundancy IS the control. (3) **It runs AFTER `requireOrgVolunteerRelationship`, not before.** First, it answers "does user X have address Y?" for any `userId` a caller submits, and user ids are not secret (`/v/[userId]` is public). Behind Guard 1 the caller is already entitled to a record the roster shows them anyway. Pinned by a test asserting `findUserIdentity` was never called when Guard 1 rejects; mutation-verified by swapping the two. (4) **The name check WARNS, it does not refuse.** `submittedNameMatchesAccount()` (`domain/background-check.ts`) is token OVERLAP, not equality — legal names and account names legitimately differ (preferred names, marriage, a roster imported holding "Bob"), so a gate would block real checks on real people. A disjoint name stamps `identityNameMismatch: true` on the audit row, spread conditionally for the same reason as `impersonatedBy`. Its suffix filter is load-bearing: without it "John Smith Jr" and "Robert Jones Jr" overlap on `jr` and the mismatch goes unrecorded. (5) **`notifyVolunteerOfCheck` still re-reads the address rather than accepting the one the guard resolved** — an address parameter there is one wrong argument from being fed `pii.email` again. One extra indexed read on a path that just made a paid third-party HTTP call is not worth trading that for. **Two things this does NOT do, and both must stay said out loud.** (a) **SSN and DOB remain unverifiable** — the platform holds no copy, so a mistyped digit still reaches the provider. (b) **Against a HOSTILE coordinator the guard proves nothing**, because staff mint the shadow user from an address they type (`addVolunteer`, `pnpm import:roster`), so they can satisfy both sides of the equality themselves. It is a MISTAKE detector — it catches the coordinator who grabbed the wrong row — not an integrity proof. This is why nothing positive is stamped on the audit row: only `identityNameMismatch` on failure, never an "identity confirmed" key that a later reader would trust. Do not describe this flow as identity-verified.

- **Credential expiry notices (v0.42.0.0)**: domain at `src/server/domain/credential-expiry.ts`, service at `credential-expiry-notice-service.ts`, queries in `credential-expiry-repo.ts`, run as one branch of the `expire-credentials` cron. Warns an org's OWNER/ADMINs 30 days before a volunteer credential lapses — one summary per org per recipient, in-app plus email, through `notify()`. Six rules, and **five of them were shipped WRONG first and caught by the pre-landing review**, so treat this entry as a list of live traps rather than history. (1) **Idempotency is per expiry CYCLE, not per row.** `notifiedAt` was filtered as `notifiedAt: null`, but `VolunteerCredential` is unique on `(userId, orgId, type)` and `upsertCredential`'s `update: data` never clears it — so re-issuing an annual background check reused the row and the credential was excluded from the scan **forever**. The feature warned once per credential and then went silent for the rest of that volunteer's tenure. `credentialNoticeCycleStart()` is the fix: a stamp older than one window necessarily describes an expiry date the row no longer has. It needs no column comparison, which matters because Prisma cannot do one without raw SQL and raw SQL here would hit the Turbopack `Prisma.sql` hazard. (2) **A self-healing story is only as good as the predicate that fires it.** Pacing was skipped on the argument that a Resend 429 leaves the batch unstamped and retries tomorrow — but the threshold was `inAppSent || emailSent === true`, and `inAppSent` is true by default, so a rate-limited batch stamped anyway and the mail was gone. `shouldStampNotifiedAt` now gates on "nobody FAILED", which keeps an opt-out (a respected preference) distinct from a bounce (a lost notice), and sends are paced at `NOTICE_SEND_DELAY_MS`. **When a docstring claims a failure self-heals, go read the predicate.** (3) **`Promise.all` in a cron that writes irreversible state is a data-loss bug** — it is fail-fast, so a sibling throwing abandoned this notifier mid-loop after it had sent real email and stamped rows, and `withCronAuth`'s catch recorded FAILURE with no `resultSummary`. `allSettled`, and the partial summary is carried into the thrown error. The route also passes ONE `now` to both credential services; they read the clock separately before, so "disjoint by construction" was false. (4) **Cap by the unit the message describes.** The email enumerates a bundle and reads as complete, so a credential-keyed cap silently truncated whichever org straddled it — and on the first production run the whole backlog is due at once, so that was the normal case. `CREDENTIAL_EXPIRY_NOTICE_ORG_CAP` caps orgs; a bundle is served whole or waits. (5) **Anything that can never satisfy its own exit condition will starve a priority queue.** An org with no OWNER/ADMIN could never be stamped, so it re-entered nightly and sorted FIRST, progressively eating the cap; it is excluded at the query (which is also where suspended orgs are filtered). (6) **The stamp and its audit row share a transaction, and `pnpm credentials:reset-notice` is the undo.** `notifiedAt` is otherwise the only record a warning was issued and it is irreversible, so a bad night could not be identified afterwards, let alone repaired. Two things this deliberately does NOT do, both P3s in `docs/TODOS.md`: only one notice per cycle (no 7-day follow-up), and the CTA links to `/app/settings/background-checks`, which renders the session's ACTIVE org — the copy names the right org, but a multi-org coordinator still has to switch manually.
