# CI, deploy and docs-site gates — full notes

Moved verbatim from `CLAUDE.md` (2026-09-28) to keep that file under Claude Code's size limit.
`CLAUDE.md` keeps a one-line rule per entry and points here; this file holds the full rationale,
history and the traps each rule was learned from. Read the relevant entry before changing the code it describes.

- CI: `.github/workflows/ci.yml` runs `pnpm lint` + `pnpm typecheck` + `pnpm typecheck:tests` + `pnpm docs:build`, `pnpm test` + `pnpm test:scripts` + `pnpm test:integration` against a `postgres:16-alpine` service container, and the deploy path — the production seed, then `pnpm next build` — against a second one, on PRs to `main` and pushes to `main`. Uses `prisma migrate deploy`, never `db push` — several migrations are hand-written SQL (triggers, functional and partial indexes) that a schema diff omits, and those are precisely what the integration specs assert. **e2e runs in CI as of 2026-08-07**, in its own `e2e` job: postgres service → `migrate deploy` → `pnpm seed:dev` → `playwright install --with-deps chromium` → `pnpm e2e`, blocking, 30-minute timeout, HTML report and traces uploaded on failure. Four rules. (1) **`seed:dev`, never a bare `pnpm seed`** — the mirror image of the `build` job's trap below: there the risk is gating `seedDev()`, a branch that never deploys; here the dev data is exactly what is wanted, because the authenticated specs look up `orgadmin@volunteermatch.local` by hand and throw "seed data missing" without it, and `seedProduction()` creates only the platform org and skill catalog. A bare `pnpm seed` resolves to the same thing today ONLY via an unset `NODE_ENV` — one job-level variable away from seeding the wrong branch. (2) **The 30-60s sequential warmup in `e2e/global-setup.ts` is not slack to optimise away** — see the `pnpm e2e` entry above; its symptom is a manifest-race 500 reported against a route unrelated to the spec that failed, which is the shape that gets a suite declared flaky and ignored. (3) **`playwright.config.ts` emits TWO reporters under CI** — `github` for inline PR annotations and `html` for the uploaded artifact — and `open: 'never'` is load-bearing, because the default (`'on-failure'`) tries to open a browser and hangs a headless runner. (4) **`scripts/e2e-ci-gate.test.ts` pins the shape**, same class as `ci-build-gate.test.ts`: deleting the job, dropping the seed or the browser install, pointing `DATABASE_URL` at a remote host, reordering migrate → seed → browsers → suite, losing the timeout or the artifact upload, and `if:`/`continue-on-error: true` are each invisible to CI's own exit code. Mutation-verified 21/21 — and it **strips comments from BOTH files it reads**, because mutation-testing caught the config assertions being satisfiable by prose: `playwright.config.ts` documents its reporter choice by quoting `open: 'never'` one line above the code, so rewriting the comment alone passed while the setting was free to change. Same lesson as `error-disclosure.guard.test.ts`, and the line-comments-before-block-comments ordering is the same too. Deliberately NOT done: the ~40s browser download is uncached (a stale browser cache is a confusing failure mode in the one job whose value is being trustworthy), and the `capture` project still does not run in CI. `src/test/integration-setup.ts` refuses a non-local `DATABASE_URL` (override: `INTEGRATION_ALLOW_REMOTE_DB=1`) because the integration specs clean up with prefix-scoped `deleteMany` sweeps. **The Biome gate has TWO independent properties — severity and reach — and it shipped broken on both** (v0.41.2.0). `pnpm lint` is `biome check . --error-on-warnings` and `pnpm check` is the same command plus `--write`; they take the SAME path (`.`) so the hook rejects whatever CI would. They used to differ — `check` carried an explicit path list omitting the root config files, so `package.json` formatting was invisible locally and caught only by CI, twice (#183, then again when `gstack-version-bump` rewrote `package.json` with spaces mid-release). (1) **Severity: `--error-on-warnings` IS the gate.** Plain `biome check` exits 0 on warn/info and fails only on error severity, so for months CI printed `Found 3 warnings` and went green while four real diagnostics sat on `main`. The `lint`-vs-`check` scope difference was NOT what let them survive — `files.includes` bounded both identically and all four were in `src/` — what differed is `--write`, and all four had Biome-**unsafe** fixes, so neither command could ever clear them. (2) **Reach: `biome check .` is NOT "whole repo."** It is bounded by `files.includes`, which omitted `scripts/**` from launch, so `import-roster.ts` (writes shadow users into a tenant and emails them), `admin-grant.ts` and `reencrypt-tokens.ts` were never linted — verified by planting `1 + "x"` in `import-roster.ts` and watching `pnpm lint` exit 0 *reporting success*. **A rule that fires on nothing and a rule that fires over the wrong half of the repo are indistinguishable from CI's exit code**, which is why `scripts/lint-gate.test.ts` pins both properties instead of trusting the command string. Three corollaries: (a) **never `--write --unsafe`** — for `noNonNullAssertion` Biome suggests `x!` → `x?.`, turning `string` into `string | undefined`; on `marketplace.ts` that produced `error TS2345` and would have broken `pnpm typecheck`. The repo's answer is `requireUserId(ctx.session)` (`server/trpc/init.ts`), since `protectedProcedure` calls `next()` without a narrowed ctx and so never narrows `ctx.session` for TypeScript. (b) **`biome.json`'s `$schema` is pinned to the INSTALLED Biome**, not `package.json`'s range — a stale schema is itself a diagnostic, and asserting the range deadlocks against lint after a lockfile-only bump (lint demands 2.4.15, the test demands 2.4.12, no edit satisfies both). (c) **`--write` repairs the working tree; git commits the index.** `.githooks/pre-commit` therefore snapshots staged files and REFUSES when Biome moves one, rather than re-staging — a partially-staged file would otherwise have its unreviewed hunks swept into the commit. Before this it printed "All checks passed" while committing the unfixed content. All of it is mutation-verified; same class as `scripts/docs-nav-links.test.ts`, guarding config the tool cannot check itself. **CI compiles the app in its own `build` job, because `pnpm typecheck` is not a substitute** (gap found v0.41.8.0, job added 2026-08-05). `next.config.ts` carries `experimental: { useTypeScriptCli: true }` because TypeScript 7 is the native Go port and ships no `lib/typescript.js`, so Next cannot load the compiler API it type-checks builds with and fails outright: *"TypeScript 7.0.2 does not provide the compiler API required by Next.js."* The flag is the alternative Next's own error message names — it spawns the `tsc` CLI as a child process instead; strictness is unchanged and the step went 9.1s → 0.4s. **As of Next 16.3 the CLI checker is the DEFAULT and the flag is redundant — it is kept explicit anyway**, because the value we need is not the one we would get by accident: `useTypeScriptCli: false` (or a future default flipping back) makes `next build` exit outright while we are on TS 7. **Do not remove it without also moving off TypeScript 7**, and note `tsconfig.json`'s `include` must keep BOTH `.next/types/**/*.ts` and `.next/dev/types/**/*.ts` or the CLI path silently loses Next's generated route types. **`next-env.d.ts` (generated, tracked) churns between the two on its own** as of 16.3: `next build` writes `./.next/types/routes.d.ts`, `next dev` writes `./.next/dev/types/routes.d.ts`, so whichever ran last wins and the file flips in `git status`. Both are correct; do not "fix" one into the other. 16.3 also adds a `root-params.d.ts` import alongside it. The reason this is a CI rule and not just a config note: dependabot #193 went **green on all three jobs** — lint+typecheck, tests, security advisories — and still broke the Vercel deploy, because `pnpm typecheck` is `tsc --noEmit`, which invokes the compiler as a *program* and passes on TS 7 either way. Only `next build` exercises the API path, and the class is wider than the Turbopack-dev-only bugs the TODO entry was originally written for — anything that fails `next build` while leaving `tsc` happy was invisible. **`scripts/vercel-build.sh` has THREE stages and the job gates the last two**: a production-only preflight, `pnpm seed`, then `next build`. It runs those two as explicit steps rather than invoking `pnpm build`, so each fails on its own line and the `VERCEL_ENV` branching stays out of CI. **The seed step is not there because the build needs data** — it does not; it is there because a broken `prisma/seed-production.ts` breaks EVERY deploy while leaving every other check green, which is the same shape as the compile gap one stage upstream. Four things were established by running the job's exact conditions locally with every `.env*` file moved aside, not by reading the code, and each is easy to "simplify" away: (1) **it needs a reachable, MIGRATED database** — `/sitemap.xml` queries organizations during static export, so with no DB the build aborts on Prisma `P1001` at 69/92 pages — though the rows may be empty, which is why migrations alone would do for the *compile*; (2) **it needs `RESEND_FROM_EMAIL`, and that is the ONLY env var beyond the workflow's existing three**, because `getFromEmail()` throws at import and `server/auth.ts` calls it at module scope, so page-data collection for `/api/auth/[...nextauth]` fails without it. It is set at JOB level deliberately, so it cannot change the behaviour of a test that observes the variable being absent; (3) **the seed step must carry `NODE_ENV: production`** — `prisma/seed.ts` DISPATCHES on it, so a bare `pnpm seed` runs `seedDev()` (demo data) and gates a branch that never deploys, which is the trap here: it looks complete and tests nothing that ships; (4) **that `NODE_ENV` belongs on the STEP, never the job** — at job level it also reaches `pnpm install --frozen-lockfile`, which then skips devDependencies and takes `next` itself out of `node_modules`. **All of it is pinned by `scripts/ci-build-gate.test.ts`**, same class as `lint-gate.test.ts`: deleting the job, swapping in `pnpm build`, dropping the database, losing `RESEND_FROM_EMAIL`, dropping the seed step or its `NODE_ENV`, and reordering any of migrate → seed → build are each invisible to CI's own exit code. **A text-presence check is not enough on its own** — `if: false` and `continue-on-error: true` both leave every string in place while removing the gate, so both are asserted against (found by an adversarial cross-model pass, which also correctly called the original compile-only job incomplete). Mutation-verified in all thirteen directions, and two of the thirteen found bugs in the guard itself — the job-missing case took the whole test FILE out of the run (a `throw` at collection time, now an empty-string return), and the first ordering mutation was vacuous because the unscoped `indexOf` matched the `test` job's migrate step. **The `useTypeScriptCli` assertion is NOT redundant with the build job**: 16.3 defaults the flag on, so deleting the line builds green today and breaks only when a future Next flips the default back. **The Node version is declared in four places and `scripts/node-version-gate.test.ts` is what compares them** (v0.42.1.0): `.nvmrc` (local shells + all five CI jobs, via `node-version-file`), `package.json` `engines.node` (**Vercel**), the workflow's `setup-node` steps, and — the one nothing declares — the floor the dependency tree actually requires. `engines` exists because without it Vercel follows its own *moving* "latest LTS available" default, which agreed with 24 by coincidence rather than declaration; the day it moves, production runs a major CI never exercised, with everything green. It is **advisory locally and binding on Vercel** — verified by execution: `engines.node: 99.x` makes `pnpm install` print `WARN Unsupported engine` and exit 0, because there is no `.npmrc` and `engine-strict` defaults to false. A `preinstall` hard-fail was considered and rejected for that reason: it would wall off a contributor before they reach any project code. **Comparing MAJORS is not enough, and the first version of the guard shipped doing only that** — `jsdom@30.0.1` declares `^22.22.2 || ^24.15.0 || >=26.0.0` and `@babel/core@8.0.1` declares `^22.18.0 || >=24.11.0`, so a major-only check stays green at `.nvmrc` `24.0` while the jsdom-backed component suite runs on a runtime its own package refuses; the test now scans `pnpm-lock.yaml` for the highest floor naming `.nvmrc`'s own major. Two traps it had to learn, both already recorded elsewhere in this file and both violated on the first draft: **strip `#` comments before scanning the workflow** (a commented-out `node-version:` is a false failure, a commented `node-version-file:` pads the count and masks a real one — same lesson as `e2e-ci-gate.test.ts`), and **do not require quotes** around `.nvmrc`, since YAML accepts a bare scalar. Mutation-verified 11/11. The exact major is deliberately NOT asserted — pinning `24` would make a Node upgrade edit this file to describe itself, which is a tautology rather than a check.

- **`Security advisories` CI gate hardening (v0.43.0.0)**: the `advisories` job in `ci.yml` (`scripts/check-advisories.ts` — `pnpm audit` against the GitHub Advisory Database, fails closed on a fixable HIGH/CRITICAL, fails OPEN with a loud announcement on everything else, see that file's own header for why `pnpm audit` and not the Dependabot alerts API) predates this entry but had no CLAUDE.md coverage until #232 found `main` carrying two CRITICAL unauthenticated Next.js RCEs unpatched for four weeks: the job had gone silently non-functional (a `pnpm.overrides` lockfile bug, fixed separately) and nothing distinguished "ran and passed" from "didn't run" in the PR checks list — both render as the same green (or absent) row. Four fixes: (1) **`buildFailOpenReport()`/`writeStepSummary()`** in `check-advisories.ts` — a fail-open run now also writes to `$GITHUB_STEP_SUMMARY` (one click from the Checks tab), not just the pre-existing `::warning` annotation that is easy to miss. (2) **`scripts/advisories-gate.test.ts`** — a fifth config guard alongside `ci-build-gate`/`lint-gate`/`e2e-ci-gate`/`node-version-gate`, mutation-tested, pinning that the job stays unconditional/blocking and that no workflow-level `paths:` filter can exclude dependency-only PRs from triggering it; its `jobBlock()`/`stripYamlComments()` helpers moved to shared `scripts/ci-gate-test-utils.ts` so the five sibling gate tests stop each carrying their own copy. (3) **`.github/workflows/security-advisories-scheduled.yml`** — a weekly `schedule:` scan independent of PR/push activity, because the literal incident window had ZERO commits and a PR-triggered gate alone does nothing when nothing is being merged. (4) **`src/app/api/cron/advisory-scan-heartbeat/`** — a Vercel cron (needs `GITHUB_ADVISORY_DISPATCH_TOKEN`, a repo-scoped `actions: write`-only fine-grained PAT) that dispatches that scheduled workflow on GitHub's behalf; it first checks the workflow's `state` and calls the `enable` endpoint when it is `disabled_inactivity` (never `disabled_manually`, a human's own call) BEFORE dispatching — three separate adversarial review passes were needed to catch that a bare `workflow_dispatch` does NOT revive a workflow GitHub has auto-disabled for 60 days of repo inactivity, so the first draft only ever sent a weekly "please go click Enable" email. `main` also has branch protection at all for the first time — see `docs/branch-protection.md` for the required-checks list and why `enforce_admins: true` is load-bearing in a solo-maintainer repo. Two known gaps, both tracked in `docs/TODOS.md`: the scheduled scan inherits the same fail-open policy with a weaker backstop (no human reads a scheduled run's summary, and GitHub's own failure-notification email doesn't fire on a fail-open exit 0), and `ci.yml`/`security-advisories-scheduled.yml` still duplicate their setup steps verbatim (enforcement divergence is caught by `advisories-gate.test.ts`; boilerplate drift is not).

- Docs site (VitePress, v0.38.5.0): **there is exactly one `DESIGN.md` (repo root) and one `TODOS.md` (`docs/`)** — there were two of each, drifted apart, and neither was a superset, so reading one and concluding you had the whole picture was a mistake several people made. `DESIGN.md` stays at the root because that is where this file sends everyone; it is therefore NOT a page on the docs site, and that is deliberate (a second copy under `docs/` is the duplication that was just removed). **Two CI checks guard the site and they are not redundant.** `pnpm docs:build` catches Vue parse errors and dead links written *in markdown* — every `.md` here is compiled as a Vue SFC, so a `{{ … }}` or a bare `<tag>` quoted in prose fails the whole build, and the error names a post-transform line number that will not match your source (backtick it). It does **NOT** validate `themeConfig.nav`/`sidebar`: verified by experiment, a `link: "/THIS_PAGE_DOES_NOT_EXIST"` in either builds green and exits 0, which is exactly how the nav spent ~5 months pointing at six `docs/guide/*` stubs deleted in 3109623. Config links are covered by `scripts/docs-nav-links.test.ts` (`pnpm test:scripts`), mutation-verified against a replay of that real regression — **do not delete it as redundant with the build step; it is the half the build cannot see.**

- **Prisma CLI datasource: `resolveCliDatabaseUrl()` in `scripts/cli-database-url.ts`**, read by `prisma.config.ts` and nothing at runtime (v0.43.1.0). **Prisma 7's config has no `directUrl`** — it used to be set behind an `as {…}` cast that hid the type error, so it was silently ignored and `migrate deploy` ran through Neon's PgBouncer pooler, which strands the session-level advisory lock and failed every later deploy with P1002. Do not re-add it, and do not cast `defineConfig`'s input. Two rules: (1) `DATABASE_URL_UNPOOLED`/`DIRECT_DATABASE_URL` is used only when it names the SAME database as `DATABASE_URL` (effective host incl. `?host=`, port, user, db, `schema`), else the CLI throws — otherwise a direct URL in `.env.local` beats a `DATABASE_URL` typed in the shell and `migrate reset` hits the file's database, which after `vercel env pull` can be production; (2) on `VERCEL_ENV=production` a missing or `-pooler` direct URL throws (at `prisma generate`, during install) rather than falling back. `scripts/vercel-build.sh` retries `migrate deploy` up to 3× on `Error: P1002` ONLY — never set `PRISMA_SCHEMA_DISABLE_ADVISORY_LOCK` instead, since two unlocked deploys can both apply one migration
