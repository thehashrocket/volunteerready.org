# Build, test and maintenance commands — full notes

Moved verbatim from `CLAUDE.md` (2026-09-28) to keep that file under Claude Code's size limit.
`CLAUDE.md` keeps a one-line rule per entry and points here; this file holds the full rationale,
history and the traps each rule was learned from. Read the relevant entry before changing the code it describes.

- `pnpm dev`: start local development server. **It rewrites two tracked generated files, and both belong in the commit** (Next 16.3): `next-env.d.ts` (route-type import paths) and an `AGENTS.md` block delimited by `<!-- BEGIN:nextjs-agent-rules -->`, which points agents at the version-matched docs bundled in `node_modules/next/dist/docs/`. Deleting the `AGENTS.md` block from a diff only makes the next `pnpm dev` re-add it as an uncommitted change; opt out with `agentRules: false` in `next.config.ts` instead, if it is ever worth losing

- `pnpm typecheck:tests` (v0.42.3.0): `tsc --noEmit --project tsconfig.tests.json`, the same compile but over test files too — `tsconfig.json` excludes `**/*.test.ts(x)` and the `vitest*.config.*` files so `pnpm typecheck` stays fast, and that exclusion hid 191 real diagnostics across 39 files (mocks inferred as zero-arg, test fixtures drifted from the domain types they exercise, a `vitest.config.mts` option that no longer exists in Vitest 5) until this gate was added and wired into CI. `tsconfig.tests.json` extends the base config without the test excludes

- `pnpm check:email-collisions`: **read-only** pre-check for T1 (email canonicalization) — finds `User` rows whose emails differ only by case, which would make a case-insensitive unique constraint fail. Prints per-row blast radius (signups/apps/orgs/creds) because `User` deletion cascades to `ShiftSignup`. Exit 1 on collisions. Safe to point at production

- `pnpm fixture:email-collisions`: **dev-only**, refuses a non-local `DATABASE_URL` (same guard shape as `e2e/utils/db.ts`). Inserts three deliberate collision groups covering each tie-break branch so the pre-check can be rehearsed. `--clean` removes them. Deliberately NOT part of `seed:dev` — these rows become invalid the moment T1's constraint lands, which would break `pnpm seed:dev` (and therefore `pnpm e2e` and the screenshot pipeline) permanently

- `pnpm import:roster --org <slug-or-id> --file <path.csv> [--dry-run] [--yes] [--actor <email>] [--no-notify] [--notify-only]`: **concierge roster import** (T17, hardened v0.41.0.0). Loads a `name,email,phone` CSV onto one org's roster through `addVolunteer()` — the same service the add form calls, so the `OrgVolunteerBlock` refusal, the shadow-user branch, first-writer-wins on `User.name` and the audit row all behave identically. A write run **requires `--yes`**; `--dry-run` needs nothing and is the intended first step every time. Unknown flags are rejected rather than ignored, so a typo'd `--dryrun` cannot silently become a live import, and **no flag may be given twice** — `--org a --org b` used to last-win silently, so one duplicated slug wrote shadow users into a stranger's tenant and emailed them. **Against a non-local `DATABASE_URL` any non-dry-run pass also requires the org's RESOLVED slug typed back at an interactive prompt** (`--dry-run` is the ONLY exemption — `--notify-only` asks too, since it emails real people; non-TTY refused, deliberately no env-var override): `--yes` cannot catch the failure that matters here, because a run aimed at the wrong org has a command line that looks exactly as intended. **Idempotent** — re-running the same file reports every row as `already on roster` and exits 0, which is what makes "fix the three bad rows and run it again" a normal thing to do

- **`--notify-only` is the recovery mode, and the audit log is the only thing that makes it possible** (v0.41.0.0). A run killed at row 55 of 60 leaves 55 rows committed and zero notices sent, and re-running the importer cannot repair it — every committed row comes back as `SKIPPED_ALREADY_ON_ROSTER`, which carries no `notify` flag. So `--notify-only` re-reads the SAME file and matches its addresses against `AuditLog` rows carrying `metadata.via = 'CONCIERGE_IMPORT'` (`findConciergeImportAuditRows`), adding nobody. Four rules: (1) **The CSV bounds the work; the audit log decides the answer.** Neither alone is right — the audit log alone is unbounded and re-emails an org's whole concierge history, while the file alone cannot tell "on the roster because this import added them" from "on the roster since last year", and would tell a five-year volunteer they were just added. (2) **Eligibility is `metadata.outcome` through `shouldNotifyByEmail`**, the same predicate the live run uses; an unrecognised outcome is its own `MALFORMED_AUDIT_ROW` status rather than folded into "never owed one", because "we cannot tell" is a different answer from "no". (3) **The `EmailEvent` dedupe is ADVISORY and reported, never a silent skip** — `sendEmail` logs SENT fire-and-forget and logs nothing at all when Resend throws, so a missing row does not prove nothing was sent, and every failure mode errs toward "we think it was sent when it was not", which is the state this mode exists to repair. `EmailEvent` also carries no `orgId`; the subject is the whole scope. (4) **Attribution comes from each audit row's own `actorId`**, resolved once per DISTINCT actor — a recovery says what the killed run would have said, so `--notify-only --actor` is refused as contradictory rather than ignored. `rosterAddedEmailSubject()` lives in `domain/org-volunteer.ts` beside `shouldNotifyByEmail` precisely so the sender and this correlation cannot drift apart

- **The roster notice reads `sendEmail`'s boolean** (v0.41.0.0). `sendRosterAddedEmail` used to `await sendEmail(...)` and discard the result, so `sendImportNotifications`' `try/catch` was dead on the likeliest failure and a 60-row import printed `notifications sent: 60` with nothing delivered. This is **the same defect fixed in `sendBackgroundCheckEmail` one version earlier**, on the same kind of email — the only notice its recipient ever gets, carrying the only link to the page where they can revoke the access. The rule was already written down here and the roster path was never audited against it: **when a rule gets recorded because one sender got it wrong, grep every other `sendEmail` caller then.** It recurred anyway: `sendAdminAlert()`/`sendImpersonationStartAlert()` in `admin-alerts.ts` discarded the same boolean until v0.43.0.0 — see that entry below for the fix (`sendToRecipients()`) and for `docs/TODOS.md`'s open follow-up on `sendAdminAlert()`'s own unmonitored failure mode. `addVolunteer`'s own fire-and-forget send moved from a bare `void` to `waitUntil` in the same pass, `.catch` still inside, with a test asserting it — reverting to `void` is otherwise invisible to the whole suite. **The deeper half of the same bug was one layer down and pre-existing**: `sendEmail` never inspected Resend's `result.error`. Resend does not throw — its response is `{ data, error: null } | { data: null, error }` — so a 429 (the exact failure the 600ms pacing exists to avoid) wrote a SENT `EmailEvent`, returned `true`, and would have made `--notify-only` skip precisely the people whose notices were lost. The error is now checked BEFORE the `EmailEvent` write, so a send that did not happen leaves no record claiming it did. **Reading a boolean is worthless if the thing computing it cannot see the failure — check the transport's own error channel, not just its exceptions.** Both notify paths go through one `sendNoticesSequentially`, which takes a per-recipient `resolveContext` callback so the live run (one context) and the recovery (one per original actor) share the pacing, the boolean handling and the streaming rather than keeping two copies

- `pnpm credentials:reset-notice --org <slug-or-id> [--since <ISO>] [--yes]` / `--audit-run <auditLogId> [--yes]`: **undo credential-expiry notice stamps** (v0.42.0.0), so a batch that was stamped but never delivered can be warned about again. `VolunteerCredential.notifiedAt` is the only record a warning was issued and there is no admin surface for it, so without this a Resend outage or a bad template leaves those credentials silent for the rest of their cycle with nothing short of hand-written production SQL to fix it. Same rails as `import:roster`, for the same reasons: a write run **requires `--yes`**, `--dry-run` needs nothing and is the intended first step every time, unknown flags are rejected rather than ignored, no flag may be given twice, and against a non-local `DATABASE_URL` a write also requires the org's RESOLVED slug typed back at an interactive prompt. `--dry-run` and `--yes` are **mutually exclusive and refused together rather than one winning** — `--dry-run` was parsed and then discarded at first, so `--org acme --dry-run --yes` cleared stamps from a command line that visibly read `--dry-run`; verified by execution during review. Both `--key=value` and `--key value` parse, because the script's own usage text prints the space form and only the equals form worked at first

- `pnpm e2e`: run Playwright e2e specs in `e2e/` (boots `pnpm dev` via `playwright.config.ts`; set `PLAYWRIGHT_BASE_URL` to target a running server instead — authenticated specs skip non-localhost targets). **A run pauses ~30-60s before the first spec**: `e2e/global-setup.ts` (wired as `globalSetup`) fetches every public route sequentially first. That is not slack to be optimised away — `webServer.url` only proves `/` answers, and in `next dev` every other route is still uncompiled, so releasing the workers onto ~20 of them at once makes Next read a `.next` manifest another compile is midway through writing and the truncated read surfaces as a 500 (`SyntaxError: Unexpected end of JSON input`). It hit `/locations/*` hardest — six slugs share one `generateStaticParams` with `dynamicParams = false`, so all six consult the prerender manifest — which is why it looked like a different spec each run and why re-running one spec alone always passed. Parallelising the warmup reproduces the stampede; it is skipped entirely when `PLAYWRIGHT_BASE_URL` is set, and it warns rather than throws so one bad route cannot take the suite down
