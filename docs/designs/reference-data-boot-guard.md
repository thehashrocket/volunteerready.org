# Reference Data Boot Guard

Generated by /plan-ceo-review on 2026-03-21
Branch: thehashrocket/fix-missing-seed-data | Mode: SELECTIVE EXPANSION

## Problem

The skill catalog (14 families, 62 skills) lives entirely in seed data
(`prisma/seed-helpers.ts`). Production seeding is manual (`pnpm seed:production`).
If the seed hasn't run, the `matching.getSkillCatalog` tRPC query returns an
empty array, and volunteers see an empty combobox on `/app/my-skills` with no
explanation. The platform org (slug: `platform`) has the same problem — if
missing, tenure badge issuance silently fails.

## Solution: Service-Layer Boot Guard

A self-healing runtime check that ensures reference data exists before serving
requests. If the skill catalog or platform org is missing, the boot guard seeds
it automatically using existing idempotent upsert logic.

### Architecture

```
src/server/domain/reference-data.ts    ← SKILL_CATALOG constant (extracted)
src/server/services/referenceDataService.ts ← ensureReferenceData()
src/server/repositories/referenceDataRepo.ts ← count/upsert queries
```

```
REQUEST ──▶ tRPC matching.getSkillCatalog
              │
              ▼
        ensureReferenceData()
              │
       ┌──────┴──────┐
       │ _seeded?     │
       │  true ──────►│──── SKIP (0ms) ────►  listSkillFamilies()
       │  false       │                              │
       │      ▼       │                              ▼
       │  count() > 0 │                         RESPONSE
       │  AND orgExists│
       │   ┌──┴──┐    │
       │   │YES  │NO  │
       │   │  seed()  │
       │   │  log()   │
       │   └──┬──┘    │
       │  _seeded=true│
       └──────┴───────┘
```

### Key Design Decisions

1. **Extract `SKILL_CATALOG` to `src/server/domain/reference-data.ts`** — pure data,
   no Prisma dependency. Both `prisma/seed-helpers.ts` and the runtime service import
   from there. Cannot import from seed-helpers directly (it creates its own PrismaClient).

2. **Module-level `_seeded` flag** — avoids re-checking on every request after first
   success. Resets on Vercel cold starts, but the count check is ~1ms.

3. **Version tracking** — `CATALOG_VERSION` constant in the domain file. The boot guard
   checks if the seeded version matches the code version, enabling incremental catalog
   updates without full re-seeds.

4. **Structured logging** — `warn` level log when boot guard fires, including family
   count, skill count, and duration. Searchable in Vercel logs.

| 12 | Public path write side-effects | Both startup + runtime guard | Belt and suspenders |
