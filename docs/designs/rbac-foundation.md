# Design: Auth Hardening + RBAC Foundation

Generated by /office-hours on 2026-03-21

Status: APPROVED (office-hours + eng review)
Mode: Startup

## Problem Statement

VolunteerReady has a working role-based auth system (4 org roles, 3 company roles, tRPC middleware procedures for each access level, multi-tenant scoping). However, platform admin is fragile (env-var-based), role/member changes are not audit-logged, and the system has no path to granular permissions when customers eventually request them.

The founder has no evidence that granular RBAC is needed today — no specific user has asked for fine-grained permissions, and the current workarounds for the target market are unknown. The goal is to harden what exists and lay a foundation that makes RBAC a small upgrade later, not a redesign.

## Demand Evidence

No direct demand evidence for granular RBAC exists. The founder acknowledges this is "enterprise instinct" rather than user-driven. The current 4-tier role hierarchy has not been tested against real users yet.

Evidence that auth hardening IS needed:
- Platform admin via `PLATFORM_ADMIN_IDS` env var is a security and operational fragility
- Role changes, member removals, and permission escalation are not audit-logged (member invitations ARE logged, but fire-and-forget — needs fix to transactional)
- Permission checks are scattered across services without a centralized model

## Status Quo

Unknown. The founder has not yet observed how nonprofit volunteer coordinators manage access control in their current tools. This is the #1 assignment coming out of this session.

## Target User & Narrowest Wedge

Not yet identified at the individual level. General target: volunteer coordinators at mid-size nonprofits (50-200 volunteers). The narrowest wedge for auth is: a platform that "just works" with sensible defaults (the current 4-tier system), with the ability to tighten permissions when a specific customer asks.

## Constraints

- Must not break existing role hierarchy (READONLY -> STAFF -> ADMIN -> OWNER)
- Must not require existing orgs to reconfigure anything (backward compatible)
- Must follow existing architecture: services -> repositories, no Prisma in routers
- Platform admin must move to DB without losing current admin access during migration
- Permission table must be additive — current middleware continues to work, permissions are checked in parallel until full migration
- Company roles (`MEMBER -> ADMIN -> OWNER`) are OUT OF SCOPE for this design — they stay as-is until a customer need emerges

## Premises

1. **The current 4-tier org role system is sufficient for pre-product and early customers.** — AGREED
2. **The highest-value auth improvement is hardening what exists (DB-backed platform admin, audit logging), not granular RBAC.** — AGREED
3. **RBAC should be designed reactively from real customer requests, not proactively from enterprise instinct.** — AGREED

## Approaches Considered

### Approach A: Auth Hardening Only (Minimal Viable)
- Move platform admin to DB
- Add permission change audit logs
- Document the existing role system
- Effort: S (human: ~2 days / CC: ~20 min)
- Risk: Low
- Pros: Ships fast, fixes real fragility, zero migration risk
- Cons: Doesn't advance toward RBAC; will redo work if RBAC is needed within 3 months

### Approach B: Auth Hardening + RBAC Foundation (Chosen)
- Everything in A
- Add a `Permission` table seeded with current implicit permissions
- Map current roles to permission sets (seed data, not UI)
- Add `hasPermission()` utility in domain layer
- No custom role UI, no role editor, no resource-level permissions
- Effort: M (human: ~1 week / CC: ~1-2 hours including tests and migration)
- Note: Step 0 procedure audit is ~2-4 hours human time (produces the spreadsheet that feeds the seed script)
- Risk: Low-Med
- Pros: Fixes today's problems AND lays groundwork. When a customer asks for custom permissions, it's a UI addition, not a schema redesign.
- Cons: Slightly more migration complexity. Permission table exists but isn't user-facing.

### Approach C: Full RBAC Now (Over-engineered)
- Custom roles, permission editor UI, role inheritance, resource-level permissions
- Effort: XL (human: ~3 weeks / CC: ~2 hours)
- Risk: High
- Pros: Enterprise-ready from day one
- Cons: No evidence anyone needs it. Massive surface area. UI complexity for an unvalidated feature.

## Recommended Approach

**Approach B: Auth Hardening + RBAC Foundation**

Rationale: It solves the real problems (fragile platform admin, no audit trail for auth events) while making the hypothetical future problem (granular RBAC) a 15-minute upgrade instead of a multi-day redesign. The Permission table is invisible to users but gives the codebase a centralized place to check access — replacing the current scattered role-rank checks over time.

### Source of Truth

**TypeScript constants are the canonical source of truth for permissions.** The runtime `hasPermission()` function reads from compiled constants in `src/server/domain/permissions.ts`, not the DB. No Permission/RolePermission DB tables in v1 — add them when a customer asks for custom roles (eng review decision: skip DB tables, constants-only).

### Implementation Outline

**0. Prerequisite: Procedure-to-Role Audit**
- Audit all tRPC routers with a three-column matrix: procedure name, middleware level, AND inline business rules (eng review decision: capture rules like ADMIN-can't-invite-ADMIN that live in routers/services, not just middleware)
- This audit produces the canonical permission constants — without it, the constants are aspirational
- Effort: ~2-4 hours human time. Output: a role x permission matrix table with business rule annotations.

**1. DB-backed Platform Admin**
- Add `isPlatformAdmin Boolean NOT NULL DEFAULT false` column to the `User` model
- Migration adds the column with default `false`. A **separate one-time seed script** (not the migration SQL itself, since migrations cannot read env vars) reads `PLATFORM_ADMIN_IDS` and sets `isPlatformAdmin = true` for those user IDs. Script location: `prisma/scripts/seed-platform-admins.ts`.
- Extract shared `isPlatformAdmin(userId)` utility in domain layer (eng review: DRY — used by both `platformAdminProcedure` and `case-study/pdf` API route, which currently has a duplicate inline check)
- `isPlatformAdmin()` queries DB on demand (`SELECT isPlatformAdmin FROM User WHERE id = ?`). Session is NOT enriched — admin routes are rare. (eng review: query on demand, session stays lean)
- Transition fallback order: DB-first, env-fallback. If `isPlatformAdmin` is `false` AND `PLATFORM_ADMIN_IDS` env var is still set, check the env var as a fallback.
- After env var removal, add a CLI escape hatch: `pnpm admin:grant <email>` script that sets `isPlatformAdmin=true`. Never get locked out. (eng review: lockout prevention)
- Remove env var fallback in this PR (not deferred). Add `PLATFORM_ADMIN_IDS` to `.env.example`.
- Seed script must be idempotent, validate user IDs exist, warn on missing IDs, report results. (eng review: edge case handling)
- **Rollback plan:** If the migration or seed fails, `PLATFORM_ADMIN_IDS` env var remains functional as the sole check during transition.

**2. Permission Constants + hasPermission()**
- NO DB tables in v1 (eng review: skip Permission/RolePermission tables — add when custom roles needed)
- TypeScript constants file at `src/server/domain/permissions.ts` with permission key definitions and role-to-permission mappings
- **Permission keys are flat.** Dots in permission keys are purely cosmetic naming conventions (`namespace.action`); no prefix-matching or wildcard logic exists in v1.
- Permission mappings based on the three-column procedure audit from step 0:
  - READONLY: read-only permissions across all modules
  - STAFF: read + operational permissions (shifts, applications)
  - ADMIN: all permissions except org-level destructive actions
  - OWNER: all permissions
- Domain utility: `hasPermission(role: Role, permission: string): boolean` — operates on an **in-memory map** built from TypeScript constants. No DB query per call.
- `hasPermission()` stays simple (role + key -> boolean). Inline business rules (ADMIN can't invite ADMIN, OWNER immutability) stay in services with comments in the constants file documenting them. (eng review: explicit > clever)

**3. Audit Logging for Auth Changes**
- Extend existing `AuditLog` table to cover: `ROLE_CHANGED`, `MEMBER_REMOVED`, `PLATFORM_ADMIN_GRANTED`, `PLATFORM_ADMIN_REVOKED`
- Fix existing `MEMBER_INVITED` audit to be transactional (currently fire-and-forget with swallowed errors)
- ALL auth-change audit events use `writeAuditLogTx` inside the same transaction as the mutation (eng review: auth audit must be transactional, not fire-and-forget)
- No new table needed — leverage existing infrastructure
- Move inline ADMIN-can't-invite-ADMIN check from `members.ts` router into `memberService.ts` (eng review: layer boundary enforcement)

**4. Centralized Permission Check + Full Migration**
- New `src/server/domain/permissions.ts` with permission constants and `hasPermission()`
- During migration, `hasPermission()` is advisory only (never blocks). When existing middleware passes but `hasPermission()` would deny, log a warning. This catches seed mismatches without breaking anything. (eng review: advisory mode with mismatch logging)
- Migrate ALL procedures in this PR, not just 3. (eng review: build it now, not deferred)
- Remove advisory mode after full migration is verified.
- Existing middleware continues to work — this is additive

**5. Documentation**
- Document the permission model in `docs/ARCHITECTURE.md`
- Add permission matrix (role x permission) to docs

## Open Questions

1. When (not if) a customer asks for custom roles, should they compose from the existing permission set, or should roles be templates that can be cloned and modified?
2. What is the exact list of permission keys? (Determined by the procedure audit in step 0)

## Success Criteria

- Platform admin is DB-backed with zero downtime migration
- All role/member changes produce audit log entries via existing AuditLog infrastructure
- `hasPermission()` utility exists and is used by ALL procedures (full migration in this PR)
- Advisory mismatch logging catches any drift between middleware and permission constants
- Existing middleware and role checks continue to work unchanged (hasPermission is advisory)
- No user-facing UI changes (this is infrastructure)

## Dependencies

- Prisma migration for new column (User.isPlatformAdmin) — NO new tables in v1
- One-time seed script for platform admin migration (`prisma/scripts/seed-platform-admins.ts`)
- CLI escape hatch script (`pnpm admin:grant <email>`)
- Three-column procedure-to-role audit (prerequisite, not a migration)
- No external dependencies

## Eng Review Decisions (2026-03-21)

1. **No DB tables** — TypeScript constants only, add Permission/RolePermission tables when custom roles needed
2. **DB-first platform admin** + CLI escape hatch (`pnpm admin:grant`) after env var removal
3. **Shared `isPlatformAdmin()` utility** — DRY, replaces duplicate check in case-study PDF route
4. **Transactional audit** for all auth changes via `writeAuditLogTx` — fix existing fire-and-forget invite audit too
5. **On-demand DB query** for platform admin — session stays lean, admin routes are rare
6. **Advisory mismatch logging** during migration — `hasPermission()` never blocks, logs warnings on disagreement
7. **Three-column procedure audit** — captures middleware level + inline business rules
8. **`hasPermission()` stays simple** — business rules (ADMIN invite restrictions, OWNER immutability) stay in services
9. **18 tests required** — unit (isPlatformAdmin, hasPermission, advisory logging), integration (transactional audit), script (seed + CLI), snapshot (permission hierarchy invariant)
10. **Full procedure migration** in this PR — not deferred

## The Assignment

**Before you write a single line of RBAC code, do this:** Find 3 volunteer coordinators at nonprofits with 50+ volunteers. Ask them to show you how they manage who-can-see-what in their current tools (whatever they use — spreadsheets, VolunteerHub, Galaxy Digital, paper). Watch them. Don't demo VolunteerReady. Just watch. Take notes on:
- Do they even think about permissions, or does everyone see everything?
- When someone needs restricted access, what do they actually do?
- Has a permissions problem ever caused a real incident (data leak, wrong person saw background check results)?

The answers will tell you whether RBAC is a top-5 priority or a top-50 priority. Build accordingly.
