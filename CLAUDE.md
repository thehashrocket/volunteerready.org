# Repository Guidelines

## Project Structure & Module Organization

This repository uses a Next.js + VitePress layout. Keep docs under `docs/`
and application code under `src/`.

- `src/`: application source code
- `tests/`: automated tests (unit/integration)
- `public/` or `assets/`: static files (images, fonts, etc.)
- `docs/`: architectural notes and user-facing docs

If you introduce a framework with a prescribed layout, follow that framework’s
conventions and document any deviations here.

## Build, Test, and Development Commands

Current commands:

- `pnpm install`: install dependencies
- `docker compose up -d db`: start the local Postgres 16 container (`docker-compose.yml`, port 5432, credentials match `DATABASE_URL` in `.env.local`). First run: `pnpm prisma migrate deploy && pnpm seed:dev`. `docker compose down -v` deletes the volume. Port 5432 is deliberate — do not remap it
- `pnpm dev`: start local development server
- `pnpm build`: build for production
- `pnpm start`: run production server
- `pnpm lint`: run Biome checks
- `pnpm format`: run Biome formatting
- `pnpm docs:dev`: run VitePress docs locally
- `pnpm docs:build`: build docs site
- `pnpm docs:preview`: preview built docs site
- `pnpm seed`: seed local dev database (reads from `.env.local`)
- `pnpm seed:production`: seed production database (run manually: `source .env.production && pnpm seed:production`)
- `pnpm seed:dev`: seed with full demo data
- `pnpm admin:grant <email>`: grant platform admin to a user
- `pnpm admin:revoke <email>`: revoke platform admin from a user
- `pnpm seed:platform-admins`: migrate `PLATFORM_ADMIN_IDS` env var to DB column (idempotent)
- `pnpm backfill:default-questions`: seed default screener questions for pre-existing orgs (idempotent, safe to re-run)
- `pnpm check:email-collisions`: **read-only** pre-check for T1 (email canonicalization) — finds `User` rows whose emails differ only by case, which would make a case-insensitive unique constraint fail. Prints per-row blast radius (signups/apps/orgs/creds) because `User` deletion cascades to `ShiftSignup`. Exit 1 on collisions. Safe to point at production
- `pnpm fixture:email-collisions`: **dev-only**, refuses a non-local `DATABASE_URL` (same guard shape as `e2e/utils/db.ts`). Inserts three deliberate collision groups covering each tie-break branch so the pre-check can be rehearsed. `--clean` removes them. Deliberately NOT part of `seed:dev` — these rows become invalid the moment T1's constraint lands, which would break `pnpm seed:dev` (and therefore `pnpm e2e` and the screenshot pipeline) permanently
- `pnpm import:roster --org <slug-or-id> --file <path.csv> [--dry-run] [--yes] [--actor <email>] [--no-notify]`: **concierge roster import** (T17). Loads a `name,email,phone` CSV onto one org's roster through `addVolunteer()` — the same service the add form calls, so the `OrgVolunteerBlock` refusal, the shadow-user branch, first-writer-wins on `User.name` and the audit row all behave identically. A write run **requires `--yes`**; `--dry-run` needs nothing and is the intended first step every time. Unknown flags are rejected rather than ignored, so a typo'd `--dryrun` cannot silently become a live import. **Idempotent** — re-running the same file reports every row as `already on roster` and exits 0, which is what makes "fix the three bad rows and run it again" a normal thing to do
- `pnpm test:scripts`: run unit tests for files under `scripts/` (uses `vitest.scripts.config.ts`, excluded from the main Vitest suite)
- `pnpm e2e`: run Playwright e2e specs in `e2e/` (boots `pnpm dev` via `playwright.config.ts`; set `PLAYWRIGHT_BASE_URL` to target a running server instead — authenticated specs skip non-localhost targets)
- `pnpm screenshots`: regenerate marketing screenshots in `public/marketing/` (Playwright `capture` project, only registered when `CAPTURE=1`; scenarios at `e2e/capture-scenarios.ts`; needs `pnpm seed:dev` data; filter with `CAPTURE_ONLY=key1,key2`)

Note: the build script (`pnpm build`) runs `pnpm db:seed` automatically on every deploy,
which includes the production seed (platform org, skill catalog, and default screener
question backfill). After a fresh production database setup, also run
`pnpm seed:production` manually to create the platform org and skill catalog.

## Coding Style & Naming Conventions

Prefer 2-space indentation for JavaScript/TypeScript and 4-space for Python.
Name files and directories using `kebab-case` and keep module names
descriptive (e.g., `user-profile.ts`, `email-service.py`). If you add a formatter
or linter (Prettier, ESLint, Black), document the exact commands and config.

## Testing Guidelines

- Test runner: Vitest (`pnpm test`)
- Unit tests: `src/**/*.test.ts` and `src/**/*.test.tsx` (colocated with source)
- Component tests: use `@testing-library/react` + jsdom; add `// @vitest-environment jsdom` to `.tsx` test files
- Test setup: `src/test-setup.ts` (jest-dom matchers + ResizeObserver polyfill)
- Integration tests excluded from `pnpm test`: `src/**/*.integration.test.ts`
- Scripts tests (separate suite): `scripts/**/*.test.ts` — run with `pnpm test:scripts`; config at `vitest.scripts.config.ts`
- E2E tests: Playwright specs in `e2e/` (`pnpm e2e`). Authenticated specs seed a NextAuth database session via `e2e/utils/db.ts` (refuses non-local `DATABASE_URL` unless `E2E_ALLOW_REMOTE_DB=1`); the dev server is the only environment that reproduces Turbopack-dev-only bugs, so bundler-sensitive fixes get e2e coverage.
- E2E cleanup + `fullyParallel`: `playwright.config.ts` sets `fullyParallel: true` (`workers: 1` in CI only), so a spec file's `beforeAll`/`afterAll` run per-worker in separate processes. A spec's `afterAll` must delete only the row IDs its own `beforeAll` created — never an unscoped sweep matching a shared literal prefix (e.g. `startsWith: PREFIX`), which can delete a sibling worker's still-in-use rows mid-test. Prefix sweeps are safe only in `beforeAll`, and only when age-gated (e.g. `createdAt < now - 30min`) so they can't catch a live sibling's fresh rows. See `e2e/esg-dashboard.spec.ts` (`cleanupIds()` vs `cleanupByPrefix()`) and the resolved P0 in `docs/TODOS.md` for the incident this pattern fixes.

## Commit & Pull Request Guidelines

Until a convention is established, use concise, imperative commit messages,
e.g., “Add API client” or “Fix build script”. Pull requests should include:

- Clear description of changes and rationale
- Linked issue or ticket (if applicable)
- Screenshots for UI changes
- Testing notes (commands run and results)

## Configuration & Secrets

Store environment-specific values in `.env` files and keep secrets out of Git.
Provide a `.env.example` with safe defaults and required keys.

- screening domain lives in `src/server/domain/volunteer-screening.ts`
- Default screener questions: `DEFAULT_SCREENER_QUESTIONS` in `volunteer-screening.ts`, seeded on org creation via `seedDefaultQuestions()` in `screenerQuestionsRepo.ts`
- RBAC permissions: `src/server/domain/permissions.ts` (constants, `hasPermission()`, role maps)
- Platform admin: `src/server/domain/platform-admin.ts` (`isPlatformAdmin()` with DB + env-var fallback)
- Advisory permission middleware: `src/server/trpc/advisory-permission-middleware.ts` (global, never blocks, logs mismatches)
- Company-scoped access: `requireCompanyAccess()` in `src/server/services/companyAccessService.ts` + the `companyScopedProcedure(opts?)` factory in `src/server/trpc/init.ts` (replaced the session-scoped `companyProcedure`/`companyAdminProcedure`/`companyPlanTierProcedure`, v0.29.2.0). Always reads `companyId` from tRPC input, never from session state — the session's "active" company can differ from the company named in the URL for a multi-company user, and authorizing off the session serves/mutates the wrong tenant. Use this factory for any new company-scoped procedure instead of reading `ctx.companyId`.
- Org↔volunteer access: `requireOrgVolunteerRelationship(orgId, userId, opts?)` in `src/server/services/orgVolunteerAccessService.ts`, backed by `findOrgVolunteerRelationship()` in `src/server/repositories/orgVolunteerRepo.ts` (v0.32.1.0). `staffProcedure` + `ctx.orgId` answer "is the caller staff, and at which org?" — neither says anything about a `userId` arriving in the procedure's **input**, and user ids are not secret (`/v/[userId]` is a public route). Any staff procedure that acts on an input-supplied `userId` must call this guard first. It accepts only relationships an org cannot mint unilaterally against a stranger — `APPLICATION`, `ORG_VOLUNTEER` (the roster row itself), `SHIFT_SIGNUP`, `ORG_MEMBER` — and deliberately excludes `VolunteerCredential`/`BackgroundCheckRequest` (circular: the write being authorized is the row that would authorize it), `VolunteerInvitation` (an outbound solicitation any staff user can create against any volunteer via the cross-org directory), and `OpportunityInterest` (a public marketplace heart-click). Throws `NOT_FOUND`, not `FORBIDDEN`, so "not yours" and "not real" are indistinguishable to a caller probing ids; `getOrgVolunteerRelationship()` is the non-throwing form for reads that render an empty state (`getOrgVisibleProfile` returns null). `acceptExistingCredential: true` is passed by `revokeCredential` and nowhere else — revocation is strictly narrowing so it cannot bootstrap itself, and without it a de-rostered volunteer's credential stays listed by `listOrgCredentials` but is permanently unrevokable. Gates `profile.getOrgVisibleProfile`, `credentials.issue`, `credentials.revoke`, and `backgroundChecks.initiate` — the last inside the shared Checkr/Sterling `initiateProviderCheck` path rather than per-caller, so it runs before the paid third-party call that receives SSN and date of birth. The returned kind is stamped onto audit metadata as `relationship`, so the authorizing edge survives a later roster soft-delete. Two things are deliberately NOT gated: `credentials.remove` (`removeCredential()` deletes on the `(userId, orgId, type)` compound key, so a stranger's row cannot match), and the FCRA resolution path `issueCredentialAndResolveFcra()`, which writes `CREDENTIAL_ISSUED` without a `relationship` key because it acts on an existing `BackgroundCheckRequest` that the guard already cleared at initiation — so audit rows from that path carry no `relationship`.
- Impersonation resolution: `resolveEffectiveUserId(realUserId, cookieValue)` in `src/server/lib/impersonation-context.ts` (v0.29.3.0) — pure function, no `getServerSession()`/`cookies()` inside it, so it resolves identically from tRPC's `createTRPCContext`, raw Route Handlers, and Server Component layout/page guards. Fails **closed**: returns `effectiveUserId: null` + `resolutionFailed: true` if a cookie was present but resolution threw — mutation paths and read-then-write SSR pages must check `resolutionFailed` and refuse rather than fall back to the real admin's identity (read-only nav/banner rendering via `getImpersonationContext()` may ignore it). Any new raw Route Handler or Server Component that reads `getServerSession()`'s `user.id` directly to scope a query/mutation must resolve through this helper instead, or it silently ignores impersonation like the bug this fixed.

- Application claiming: an orphan application (`submittedByUserId: null`) is **never** bound to a user implicitly. `screener.submit` is a `publicProcedure` accepting an arbitrary `submittedByEmail`, so orphan rows are attacker-controllable, and binding one mints an `APPLICATION` edge that `requireOrgVolunteerRelationship()` accepts as authorization for `profile.getOrgVisibleProfile` and `credentials.issue`. The predecessor `linkApplicationsToUser()` auto-bound every address match on each `/app/my-applications` load and was a live privilege escalation (fixed 2026-07-27). Binding now goes through `claimApplication()` in `my-applications.ts` → `claimApplicationForUser()` in `volunteer-applications.ts`, which enforces the email match **inside the Prisma `where` clause** — not a caller-side comparison — so a foreign application id matches zero rows. If you add another path that attaches an application to a user, it must go through this function or repeat its `where`.
- **Never use Prisma's `mode: 'insensitive'` on an authorization predicate.** It compiles to `ILIKE $1` with the value interpolated **unescaped**, so `_` and `%` become wildcards — and `_` is legal in an address `zod.email()` accepts. Verified in Postgres: `'jason.shultz@x' ILIKE 'jason_shultz@x'` is TRUE, so `j_smith@…` would match (and claim) `j.smith@…`'s row. This shipped briefly in the claim flow and was caught in review. Compare identities with plain equality against `normalizeEmail()`. Storage is kept canonical instead: T1's migration backfilled `VolunteerApplication.submittedByEmail`, and `screener.submit` normalizes on write via `.transform(normalizeEmail)`. Three regression tests in `applicationClaim.integration.test.ts` go red if `insensitive` is reintroduced.
- **`ctx.session.user.email` is NOT the effective user's address.** `createTRPCContext` builds the session as `{ ...realSession.user, id: effectiveUserId }` — under impersonation only `id` is swapped, so the email stays the *real admin's*. Any code pairing `session.user.id` with `session.user.email` is mixing two identities. Resolve the address from the id with `findEmailByUserId()` (`userAccountStateRepo.ts`) instead; `claimApplication`/`listClaimableApplications` take only a user id for exactly this reason. Also fixed in `getVolunteerDashboard`, `acceptInvitation` (`memberService.ts`) and `acceptCompanyInvite` (`companyService.ts`) in v0.34.0.0 — all three dropped the email **parameter** rather than just its usage, because while the parameter exists every call site is one `session.user.email` away from restoring the bug.
- Roster convergence (E1a, v0.34.0.0): `ensureAppliedRosterRow()` in `src/server/services/appliedRosterService.ts` materializes the `OrgVolunteer` edge an approved application implies, called from **both** `updateOrgApplicationStatus()` (`screener-queries.ts`) and `claimApplication()` (`my-applications.ts`) inside their existing transactions. Two rules that are easy to break: (1) it inserts via `createOrgVolunteerIfAbsent()` — a `createMany({ skipDuplicates: true })`, i.e. `ON CONFLICT DO NOTHING` — **not** `findFirst`+`create`+catch-P2002, which is what the design doc originally prescribed. Verified against Postgres: swallowing a P2002 inside `prisma.$transaction` poisons the transaction (`current transaction is aborted`), so a concurrent roster race would roll back the enclosing approval. `addVolunteer` keeps the catch-outside shape because there the duplicate IS the answer the coordinator needs. (2) The approval callsite gates on the **transition** (`previousStatus !== 'APPROVED'`), not on `status === 'APPROVED'`, because that mutation is not idempotent and gating on status alone resurrects a deliberately-removed volunteer (the soft-deleted row does not block a fresh insert). Anonymous applications (`submittedByUserId: null`) are deliberately excluded until v1b, so an org with anonymous applicants carries a partial roster — do not describe the roster as complete.
- Claimable-application decline (v0.34.0.0): `declinedByUserId`/`declinedAt` on `VolunteerApplication`, written only by `declineApplicationForUser()`, which enforces the email match **inside the `where`** exactly as the claim does. Declining is terminal, and that is enforced in BOTH `listClaimableApplicationsByEmail` **and** `claimApplicationForUser`'s `where` — filtering the listing alone left the mutation reachable from a stale client cache (two tabs: decline in one, claim in the other), which re-mints the very edge the user refused. Two nullable columns rather than a join table because `User.email` is unique and canonicalized and claimability is email equality — for any orphan row exactly ONE user can ever claim it. The "Not mine" control keeps the same size and variant as "Add to my account" (a test compares their `className`): declining is the safe action here, so it must not read as weaker or more dangerous than accepting.
- Assign-to-shift (T8/T24, v0.35.0.0): `assignVolunteerToShift()` in `shiftSignupService.ts`, surfaced by `AssignVolunteerPicker` inside `ShiftDetailDialog`. Four rules that are easy to break: (1) it takes an **`OrgVolunteer.id`, never a `User.id`** — `getRoster` deliberately withholds `userId` from clients (it is a cross-tenant correlation handle), so the user id is derived server-side via `findOrgVolunteerById(orgId, id)`, which also makes the org relationship true by construction rather than needing `requireOrgVolunteerRelationship`. (2) **Reassignment is not idempotent**, contrary to what the design doc claimed: `createSignup` only creates and `validateSignup`'s duplicate check matches `CONFIRMED` alone, so a CANCELLED/ATTENDED/NO_SHOW row for the same pair reached `ShiftSignup @@unique([shiftId, userId])` as an unhandled 500. The service resolves the existing row first — CANCELLED and WAITLISTED are revived to CONFIRMED on the same row, the other three refused by name. (3) **`allowOverCapacity` is an option ON `validateSignup`, not a filter on its result.** Every refusal there returns early, so ignoring the `SHIFT_FULL`/`AT_CAPACITY` codes at the service would also ignore that the duplicate and time-conflict checks never ran; skipping only the capacity block lets execution fall through to them. (4) The picker's candidate list **must** be computed server-side (`listAssignableVolunteers`): roster rows are keyed by `OrgVolunteer.id` and signups by `User.id`, so the client has no join key with which to exclude people already on the shift. Staff disclosure differs from the volunteer path on purpose — `mapSignupFailure` collapses cancelled/completed to NOT_FOUND because `shifts.signup` is open to strangers, while staff own the shift and get the real reason.
- Roster feature-flag gating (v0.35.0.0): `rosterProcedure` lives in `src/server/trpc/roster-flag-middleware.ts`, shared by `routers/volunteers.ts` and `routers/shifts.ts` — the roster's central mutation is on `shifts`, and a hand-copied flag check in a second router is the one that gets missed when the flag retires. Server Components resolve the same flag through `resolveVolunteerRosterFlag()` in `src/server/lib/roster-flag.ts`, which fails closed on impersonation-resolution failure, no resolvable org, or the flag being off. There is **no client flag-read path**, and adding one would flash gated surfaces in after hydration — which is why `shifts/page.tsx` is a Server Component wrapping `ShiftsClient` rather than reading the flag over tRPC. `app/(app)/app/layout.tsx` keeps its own inline resolution deliberately: it already holds `membershipOrgIds` for the `hasOrg` guard, so routing it through the helper would issue that query twice per request. **Two roster procedures are deliberately UNGATED, on a third router**: `profile.listMyOrgMemberships` and `profile.leaveOrgRoster` (T32, v0.36.0.0), under plain `protectedProcedure`. `ensureAppliedRosterRow` mints roster edges for every org regardless of the flag, so gating the volunteer's **exit** would strand people on rosters they cannot leave — the design doc's gating table states this. Do not "make them consistent" by moving them onto `rosterProcedure`; `routers/profile.leave.test.ts` goes red if you do. Corollary: grepping `rosterProcedure` does NOT enumerate every roster surface when the flag retires. **Grep `isRosterEnabledForOrg` instead** (v0.38.0.0) — the predicate moved to `featureFlagService.ts` when Lane G gave it SIX callers of three different shapes: `rosterProcedure`, two Server Components (`app/(app)/app/layout.tsx`'s nav gate and `resolveVolunteerRosterFlag()`), the roster CSV Route Handler, and the two onboarding surfaces. The sixth was missed on the first pass — `layout.tsx` still resolved the flag inline while this very rule said the grep was complete, which is why the count is spelled out here. **The concierge importer checks no flag at all and so matches neither grep**; that may be the right concierge sequence (load the roster, then flip the flag) but nothing states it — tracked as a P3. It lives in the service rather than in `lib/roster-flag.ts` where it started because that module imports next-auth and `next/headers` to resolve a session, which the tRPC middleware and the onboarding queries should not take on for a one-line flag read.
- Volunteer self-service leave (T32, v0.36.0.0): `leaveOrgRoster()` in `staffVolunteerService.ts` → `softDeleteOwnOrgVolunteerByOrg()` in `orgVolunteerRepo.ts` (was `softDeleteOwnOrgVolunteer()`, deleted in v0.37.0.0 when leaving became org-keyed), surfaced as the "Organizations you volunteer with" card on `/app/profile`. The `userId` sits inside the Prisma `WHERE` of **both** the read and the `updateMany` — mutation-verified: dropping it from one statement leaves the security test green (the other still guards), dropping it from both turns it red, so neither is dead code. Returns the soft-deleted ROW id (v0.37.0.0; it returned `orgId` when leaving was id-keyed), which the `VOLUNTEER_LEFT` audit row points at. The audit `orgId` now comes from the caller's input, because the client DOES name an org — see the next entry. Leaving **is a revocation** as of v0.37.0.0 — see the next entry. It was not when T32 shipped, and the copy at the time said so.
- Volunteer revocation via `OrgVolunteerBlock` (v0.37.0.0): `leaveOrgRoster()` writes a block row in the same transaction as the soft delete, and `findOrgVolunteerRelationship()` suppresses every relationship kind except `ORG_MEMBER` and `EXISTING_CREDENTIAL` when one exists (both exemptions explained below — do not read the first clause alone). This exists because **every other edge in that guard is one staff can mint unilaterally** — `addVolunteer` takes an email address and needs no consent — so soft-deleting the roster row left the volunteer with no state the org could not recreate in two clicks. The rejected alternative (cancel the signups, filter `CANCELLED` out of the `SHIFT_SIGNUP` probe) fails for exactly that reason, and the pre-fix confirm copy admitted it: *"and they can add you again."* Four rules that are easy to break: (1) **`ORG_MEMBER` is exempt and the suppression path RE-PROBES for it** — a coordinator who is also on their own org's roster would otherwise lock themselves out of their own organization by leaving it, and only when they had also applied, since the probe short-circuits at `APPLICATION` and never reaches the member check. (2) **The block check runs AFTER the probes, not before** — blocks are rare, so checking first adds a query to every call to save one on almost none; the rejection path stays at four queries and the accept path pays one indexed lookup. (3) **Lifting is volunteer-initiated only**, via `liftOrgVolunteerBlock()` in `orgVolunteerAccessService.ts`, called from application submit (only when `submittedByUserId` is set — `screener.submit` is a `publicProcedure` and an attacker-supplied address must not clear a block), `claimApplication`, and `signUpForShift`. Adding an org-initiated lift would hand the revocation back to the party it protects against. In `claimApplication` it must run **before** `ensureAppliedRosterRow`, or the roster row is minted while the block still stands. (4) **`addVolunteer` refuses with FORBIDDEN, not the guard's NOT_FOUND** — that guard hides "not yours" behind "not real" because it takes a `userId` from input, but here the org already had this person on its roster, so there is nothing to conceal. Mutation-verified against real Postgres in `orgVolunteer.integration.test.ts`; note the `ORG_MEMBER` test there carries a deliberate `VolunteerApplication` so the probe cannot short-circuit past the block, or it would pass vacuously. **`EXISTING_CREDENTIAL` is exempt too** — suppressing it recreated the dead end `acceptExistingCredential` exists to prevent (a credential `listOrgCredentials` still shows but nobody can ever revoke), and revocation is strictly narrowing so a block has nothing to protect against there. **Count the two sets separately.** There are THREE roster-row CREATORS — `addVolunteer`, `ensureAppliedRosterRow`, `restoreVolunteer` — and FOUR paths that refuse while a block stands, the fourth being `assignVolunteerToShift`, which creates no roster row but ACTS on one. `restoreVolunteer` is the creator that does not look like a create and was missed until five review specialists caught it, because `restoreOrgVolunteer` matches any row with `deletedAt` set and nothing records WHO deleted it. A new-path rule phrased as "creates a roster row" would not catch the assign case; the rule is **creates OR acts on** one. **The concierge importer (T17, v0.38.0.0) is the first new path since, and it needed no new refusal** — precisely because it writes through `addVolunteer()` rather than reimplementing the insert, so it inherits the block check for free and reports the refusal per row. That is the pattern for any future bulk path: go through the service, do not repeat the guard.
- Leaving is keyed on `orgId`, not `OrgVolunteer.id` (v0.37.0.0): `listMyOrgRelationships()` lists every org holding ANY authorizing edge — roster row, `VolunteerApplication`, or `ShiftSignup` — not just live roster rows. The roster-row-only listing let an org **deny the remedy**: remove the volunteer, and the row vanished from their profile along with the Leave button, while the surviving `SHIFT_SIGNUP` kept satisfying `findOrgVolunteerRelationship` and with it `backgroundChecks.initiate`. So an org that saw a departure coming could pre-empt it. Consequences: the soft delete is now the OPTIONAL half (`softDeleteOwnOrgVolunteerByOrg` returning null is normal, not an error) and the block is the mandatory one; `hasLeavableOrgRelationship()` is a required precondition, since `orgId` is caller-supplied and without it any user could mint blocks against arbitrary orgs; `orgId` IS projected to the client now (an org with no roster row has no row id to name it by); and `ORG_MEMBER` never puts an org on the list by itself but is surfaced as `isStaff`, because the block exempts it and the confirm would otherwise promise a revocation that does not happen for staff at their own org. `MY_ORG_RELATIONSHIP_COPY` is a `Record` over four reasons for the same reason `ORG_VOLUNTEER_SOURCE_COPY` is: a new reason must be a type error, not a silently wrong sentence on a consent surface.
- **Disclosure surfaces derive from the definition, never a hand-maintained copy** (v0.37.2.0). When a legal or consent surface enumerates something the code defines — the `/privacy` third-party table, `/terms` §6, roster-relationship copy — bind it to that definition so a new member is a **type error or a red test**, never a silently incomplete disclosure. - Concierge roster import + export + metrics (Lane G, v0.38.0.0). Three surfaces that together make the roster loadable, portable and measurable. Rules worth keeping: (1) **The importer writes through `addVolunteer()`**, never a parallel insert — see the block rule above. Provenance is `metadata.via = 'CONCIERGE_IMPORT'` on the audit row, and deliberately NOT a third `OrgVolunteerSource`: the success metric counts `STAFF_ADDED`, and splitting the enum would drop every concierge-onboarded org out of the metric the concierge motion exists to move. (2) **The importer opts out of `addVolunteer`'s notification** (`sendNotification: false`, new) and sends them itself afterwards — sequential, awaited, failures reported. The service's own send is fire-and-forget behind `.catch(console.error)`, which is right for one coordinator clicking Add and wrong for sixty rows against a rate limiter; the people owed that email are exactly those added from a spreadsheet they never saw, and it carries the only link to the surface where they can revoke the access. (3) **`findOrgByIdOrSlug` resolves id FIRST, as two `findUnique` calls** — never one `findFirst` with `OR: [{id},{slug}]`. `Organization.id` is a cuid and `ORG_SLUG_PATTERN` accepts exactly that shape, so an org can register another org's id as its slug and win an unordered `findFirst`, pointing a concierge import at the squatter. Any new `/api/org/[orgId]/**` handler must use it. `roleRank` moved to `domain/permissions.ts` at the same time — there were already two private copies. (5) **The export is FREE-tier on purpose** (`domain/roster-export.ts`): an org that cannot get its data back out has not chosen to stay. (6) **CLI switches must reject a VALUE, not just an unknown name.** `flags.get('dry-run') === true` fails OPEN when the flag carries one: `--dry-run=false --yes` ran a live production write from a command line that visibly read `--dry-run`. Guarding the typo'd NAME (`--dryrun`) is not enough. (7) **`countOrgsWithPopulatedRoster` reports TWO different measures.** Funnel step 5 is "≥`ROSTER_POPULATED_THRESHOLD` live rows, any source, any time", matching the checklist and the concierge offer so the product cannot congratulate an org it is still nudging. `rosterActivation` is the launch's primary success metric — `STAFF_ADDED` only, within 7 days of signup — and is rendered as its own card rather than a sixth funnel bar, because it answers a different question. (8) **The onboarding roster step is OMITTED when the flag is off**, not shown-and-incomplete: it links to `/app/volunteers`, which redirects a non-pilot org away, and counting it would peg those orgs at "4 of 5" forever.
- CSV: one parser and one writer, in `src/server/domain/csv.ts` (`parseCsvRecords`, `escapeCsvField`, `toCsvLine`). RFC 4180 — quoted fields, embedded commas and newlines, `""` escapes, BOM stripping, CRLF/LF/CR. A naive `split(',')` is wrong for the files this actually receives: real volunteer spreadsheets contain `"Smith, Jane"`, and splitting shifts every later column left so the email field arrives holding a first name. `escapeCsvField` moved here from `esg-report.ts` (which re-exports it) when the roster export became its second consumer — two copies of a formula-injection guard is where one of them stops being maintained. Three rules that pre-landing review had to teach this module the hard way: (1) **`\r` is in the must-quote set.** It was not, and `parseCsvRecords` treats a lone CR as a record terminator, so a volunteer-controlled `displayName` of `Jane\r=cmd|…` broke out of its field and the payload led a NEW record — where the formula prefix never applies. (2) **`FORMULA_LEAD` allows leading whitespace**, because Excel and Sheets trim before deciding a cell is a formula, so `\t=SUM(A1)` still executes. (3) **`unescapeCsvField` exists because our own export is an input to our own importer.** Without it a re-imported `+1 555 0100` persisted as `'+1 555 0100` — every international phone number — silently, since `volunteerPhoneSchema` accepts a leading apostrophe. An unterminated quote is now a `CsvFormatError` rather than swallowing the rest of the file into one field, which previously reported "0 valid, 1 invalid — Email is required" for a 60-row spreadsheet. `bulk-import-service.parseCsv` (the applications importer) still has its own naive parser; converting it is a separate open TODO.
- Raw SQL: never compose `Prisma.sql` fragments (via `Prisma.join`, conditional `Prisma.sql`/`Prisma.empty`) and interpolate them into `$queryRaw` templates. Turbopack dev duplicates the generated client's `Sql` class across module graphs, `instanceof` fails, and the fragment is sent to Postgres as one literal parameter ("invalid input syntax" 500s that only reproduce under `next dev`). Write one static template with NULL-checked optional filters instead — prefer the sargable form `col >= COALESCE(${x}::timestamp, '-infinity'::timestamp)` for range filters (index-friendly under generic plans), or `(${x}::type IS NULL OR col = ${x}::type)` for types without ±infinity (booleans etc.).
- No Prisma calls in tRPC routers. Routers call services. Services call repositories. Period.
- All DB writes go through services (so audit logging is automatic).
- Every table gets createdAt, updatedAt, and if relevant deletedAt. Soft delete now saves you.
- Zod schemas live next to domain models and get imported on both sides. No duplicating.
