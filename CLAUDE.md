# Repository Guidelines

## Project Structure & Module Organization

This repository uses a Next.js + VitePress layout. Keep docs under `docs/`
and application code under `src/`.

- `src/`: application source code
- `tests/`: automated tests (unit/integration)
- `public/` or `assets/`: static files (images, fonts, etc.)
- `docs/`: architectural notes and user-facing docs

If you introduce a framework with a prescribed layout, follow that framework’s
conventions and document any deviations here.

## Build, Test, and Development Commands

Current commands:

- `pnpm install`: install dependencies
- `docker compose up -d db`: start the local Postgres 16 container (`docker-compose.yml`, port 5432, credentials match `DATABASE_URL` in `.env.local`). First run: `pnpm prisma migrate deploy && pnpm seed:dev`. `docker compose down -v` deletes the volume. Port 5432 is deliberate — do not remap it
- `pnpm dev`: start local development server
- `pnpm build`: build for production
- `pnpm start`: run production server
- `pnpm lint`: run Biome checks
- `pnpm format`: run Biome formatting
- `pnpm docs:dev`: run VitePress docs locally
- `pnpm docs:build`: build docs site
- `pnpm docs:preview`: preview built docs site
- `pnpm seed`: seed local dev database (reads from `.env.local`)
- `pnpm seed:production`: seed production database (run manually: `source .env.production && pnpm seed:production`)
- `pnpm seed:dev`: seed with full demo data
- `pnpm admin:grant <email>`: grant platform admin to a user
- `pnpm admin:revoke <email>`: revoke platform admin from a user
- `pnpm seed:platform-admins`: migrate `PLATFORM_ADMIN_IDS` env var to DB column (idempotent)
- `pnpm backfill:default-questions`: seed default screener questions for pre-existing orgs (idempotent, safe to re-run)
- `pnpm check:email-collisions`: **read-only** pre-check for T1 (email canonicalization) — finds `User` rows whose emails differ only by case, which would make a case-insensitive unique constraint fail. Prints per-row blast radius (signups/apps/orgs/creds) because `User` deletion cascades to `ShiftSignup`. Exit 1 on collisions. Safe to point at production
- `pnpm fixture:email-collisions`: **dev-only**, refuses a non-local `DATABASE_URL` (same guard shape as `e2e/utils/db.ts`). Inserts three deliberate collision groups covering each tie-break branch so the pre-check can be rehearsed. `--clean` removes them. Deliberately NOT part of `seed:dev` — these rows become invalid the moment T1's constraint lands, which would break `pnpm seed:dev` (and therefore `pnpm e2e` and the screenshot pipeline) permanently
- `pnpm import:roster --org <slug-or-id> --file <path.csv> [--dry-run] [--yes] [--actor <email>] [--no-notify] [--notify-only]`: **concierge roster import** (T17, hardened v0.41.0.0). Loads a `name,email,phone` CSV onto one org's roster through `addVolunteer()` — the same service the add form calls, so the `OrgVolunteerBlock` refusal, the shadow-user branch, first-writer-wins on `User.name` and the audit row all behave identically. A write run **requires `--yes`**; `--dry-run` needs nothing and is the intended first step every time. Unknown flags are rejected rather than ignored, so a typo'd `--dryrun` cannot silently become a live import, and **no flag may be given twice** — `--org a --org b` used to last-win silently, so one duplicated slug wrote shadow users into a stranger's tenant and emailed them. **Against a non-local `DATABASE_URL` any non-dry-run pass also requires the org's RESOLVED slug typed back at an interactive prompt** (`--dry-run` is the ONLY exemption — `--notify-only` asks too, since it emails real people; non-TTY refused, deliberately no env-var override): `--yes` cannot catch the failure that matters here, because a run aimed at the wrong org has a command line that looks exactly as intended. **Idempotent** — re-running the same file reports every row as `already on roster` and exits 0, which is what makes "fix the three bad rows and run it again" a normal thing to do
- **`--notify-only` is the recovery mode, and the audit log is the only thing that makes it possible** (v0.41.0.0). A run killed at row 55 of 60 leaves 55 rows committed and zero notices sent, and re-running the importer cannot repair it — every committed row comes back as `SKIPPED_ALREADY_ON_ROSTER`, which carries no `notify` flag. So `--notify-only` re-reads the SAME file and matches its addresses against `AuditLog` rows carrying `metadata.via = 'CONCIERGE_IMPORT'` (`findConciergeImportAuditRows`), adding nobody. Four rules: (1) **The CSV bounds the work; the audit log decides the answer.** Neither alone is right — the audit log alone is unbounded and re-emails an org's whole concierge history, while the file alone cannot tell "on the roster because this import added them" from "on the roster since last year", and would tell a five-year volunteer they were just added. (2) **Eligibility is `metadata.outcome` through `shouldNotifyByEmail`**, the same predicate the live run uses; an unrecognised outcome is its own `MALFORMED_AUDIT_ROW` status rather than folded into "never owed one", because "we cannot tell" is a different answer from "no". (3) **The `EmailEvent` dedupe is ADVISORY and reported, never a silent skip** — `sendEmail` logs SENT fire-and-forget and logs nothing at all when Resend throws, so a missing row does not prove nothing was sent, and every failure mode errs toward "we think it was sent when it was not", which is the state this mode exists to repair. `EmailEvent` also carries no `orgId`; the subject is the whole scope. (4) **Attribution comes from each audit row's own `actorId`**, resolved once per DISTINCT actor — a recovery says what the killed run would have said, so `--notify-only --actor` is refused as contradictory rather than ignored. `rosterAddedEmailSubject()` lives in `domain/org-volunteer.ts` beside `shouldNotifyByEmail` precisely so the sender and this correlation cannot drift apart
- **The roster notice reads `sendEmail`'s boolean** (v0.41.0.0). `sendRosterAddedEmail` used to `await sendEmail(...)` and discard the result, so `sendImportNotifications`' `try/catch` was dead on the likeliest failure and a 60-row import printed `notifications sent: 60` with nothing delivered. This is **the same defect fixed in `sendBackgroundCheckEmail` one version earlier**, on the same kind of email — the only notice its recipient ever gets, carrying the only link to the page where they can revoke the access. The rule was already written down here and the roster path was never audited against it: **when a rule gets recorded because one sender got it wrong, grep every other `sendEmail` caller then.** `addVolunteer`'s own fire-and-forget send moved from a bare `void` to `waitUntil` in the same pass, `.catch` still inside, with a test asserting it — reverting to `void` is otherwise invisible to the whole suite. **The deeper half of the same bug was one layer down and pre-existing**: `sendEmail` never inspected Resend's `result.error`. Resend does not throw — its response is `{ data, error: null } | { data: null, error }` — so a 429 (the exact failure the 600ms pacing exists to avoid) wrote a SENT `EmailEvent`, returned `true`, and would have made `--notify-only` skip precisely the people whose notices were lost. The error is now checked BEFORE the `EmailEvent` write, so a send that did not happen leaves no record claiming it did. **Reading a boolean is worthless if the thing computing it cannot see the failure — check the transport's own error channel, not just its exceptions.** Both notify paths go through one `sendNoticesSequentially`, which takes a per-recipient `resolveContext` callback so the live run (one context) and the recovery (one per original actor) share the pacing, the boolean handling and the streaming rather than keeping two copies
- `pnpm test:scripts`: run unit tests for files under `scripts/` (uses `vitest.scripts.config.ts`, excluded from the main Vitest suite)
- `pnpm e2e`: run Playwright e2e specs in `e2e/` (boots `pnpm dev` via `playwright.config.ts`; set `PLAYWRIGHT_BASE_URL` to target a running server instead — authenticated specs skip non-localhost targets). **A run pauses ~30-60s before the first spec**: `e2e/global-setup.ts` (wired as `globalSetup`) fetches every public route sequentially first. That is not slack to be optimised away — `webServer.url` only proves `/` answers, and in `next dev` every other route is still uncompiled, so releasing the workers onto ~20 of them at once makes Next read a `.next` manifest another compile is midway through writing and the truncated read surfaces as a 500 (`SyntaxError: Unexpected end of JSON input`). It hit `/locations/*` hardest — six slugs share one `generateStaticParams` with `dynamicParams = false`, so all six consult the prerender manifest — which is why it looked like a different spec each run and why re-running one spec alone always passed. Parallelising the warmup reproduces the stampede; it is skipped entirely when `PLAYWRIGHT_BASE_URL` is set, and it warns rather than throws so one bad route cannot take the suite down
- `pnpm screenshots`: regenerate marketing screenshots in `public/marketing/` (Playwright `capture` project, only registered when `CAPTURE=1`; scenarios at `e2e/capture-scenarios.ts`; needs `pnpm seed:dev` data; filter with `CAPTURE_ONLY=key1,key2`)

Note: the build script (`pnpm build`) runs `pnpm db:seed` automatically on every deploy,
which includes the production seed (platform org, skill catalog, and default screener
question backfill). After a fresh production database setup, also run
`pnpm seed:production` manually to create the platform org and skill catalog.

## Coding Style & Naming Conventions

Prefer 2-space indentation for JavaScript/TypeScript and 4-space for Python.
Name files and directories using `kebab-case` and keep module names
descriptive (e.g., `user-profile.ts`, `email-service.py`). If you add a formatter
or linter (Prettier, ESLint, Black), document the exact commands and config.

## Testing Guidelines

- Test runner: Vitest (`pnpm test`)
- Unit tests: `src/**/*.test.ts` and `src/**/*.test.tsx` (colocated with source)
- Component tests: use `@testing-library/react` + jsdom; add `// @vitest-environment jsdom` to `.tsx` test files
- Test setup: `src/test-setup.ts` (jest-dom matchers + ResizeObserver polyfill)
- Integration tests excluded from `pnpm test`: `src/**/*.integration.test.ts`
- Scripts tests (separate suite): `scripts/**/*.test.ts` — run with `pnpm test:scripts`; config at `vitest.scripts.config.ts`
- E2E tests: Playwright specs in `e2e/` (`pnpm e2e`). Authenticated specs seed a NextAuth database session via `e2e/utils/db.ts` (refuses non-local `DATABASE_URL` unless `E2E_ALLOW_REMOTE_DB=1`); the dev server is the only environment that reproduces Turbopack-dev-only bugs, so bundler-sensitive fixes get e2e coverage.
- E2E cleanup + `fullyParallel`: `playwright.config.ts` sets `fullyParallel: true` (`workers: 1` in CI only), so a spec file's `beforeAll`/`afterAll` run per-worker in separate processes. A spec's `afterAll` must delete only the row IDs its own `beforeAll` created — never an unscoped sweep matching a shared literal prefix (e.g. `startsWith: PREFIX`), which can delete a sibling worker's still-in-use rows mid-test. Prefix sweeps are safe only in `beforeAll`, and only when age-gated (e.g. `createdAt < now - 30min`) so they can't catch a live sibling's fresh rows. See `e2e/esg-dashboard.spec.ts` (`cleanupIds()` vs `cleanupByPrefix()`) and the resolved P0 in `docs/TODOS.md` for the incident this pattern fixes.
- E2E route warmup: `e2e/global-setup.ts` compiles every public route sequentially before the workers start — see the `pnpm e2e` entry above for why. Its route list is **derived** from `PUBLIC_PAGES` (`src/lib/public-pages.ts`) plus `LOCATIONS`, never retyped: the first hand-written draft already omitted `/map` and `/search`, and a route missing here fails as the manifest-race 500 reported against an unrelated page. Adding a public page needs no change here; adding an *authenticated* route does (they are deliberately absent — they need a seeded session).
- E2E layout assertions: `e2e/utils/layout.ts` — `expectNoHorizontalOverflow(page, width)` (document-level, and it names the widest node so a failure is a fix rather than a bisect), `expectNoInternalScroll(page, selector)`, `expectEllipsized(page, selector)`. **All three are different properties; a document-level check alone is necessary but not sufficient.** A `Table`'s own `overflow-auto` wrapper scrolls internally while the document stays exactly the viewport width, and content can break its container yet still stop inside the viewport (`/app/opportunities`' header actions ran 32px past the page padding and ended at exactly 375, so every overflow assertion passed while the button sat flush against the edge). Where a container's bounds are the requirement, assert against the container and measure the widest DESCENDANT, not the wrapper. `expectEllipsized` needs a fixture string with **no line-break opportunities** — underscores and letters, never spaces or hyphens (UAX #14 class BA), or the text wraps instead of overflowing and the assertion passes vacuously. The **768-1023px band is the load-bearing viewport**, not 375px. Consumers: `e2e/staff-tables-mobile.spec.ts` (applications, opportunities, shifts, team) and `e2e/staff-created-volunteers.spec.ts` (the roster).

## Commit & Pull Request Guidelines

Until a convention is established, use concise, imperative commit messages,
e.g., “Add API client” or “Fix build script”. Pull requests should include:

- Clear description of changes and rationale
- Linked issue or ticket (if applicable)
- Screenshots for UI changes
- Testing notes (commands run and results)

## Rules

- app/** = routing + page composition only
- server/services/** = business logic (SOLID home base)
- server/repositories/** = Prisma access only
- server/domain/** = types + invariants + pure functions
- server/trpc/** = routers + procedures only (thin)
- screening domain lives in `src/server/domain/volunteer-screening.ts`
- Default screener questions: `DEFAULT_SCREENER_QUESTIONS` in `volunteer-screening.ts`, seeded on org creation via `seedDefaultQuestions()` in `screenerQuestionsRepo.ts`
- RBAC permissions: `src/server/domain/permissions.ts` (constants, `hasPermission()`, role maps)
- **The ADMIN tier is OWNER-granted only, and it has TWO doors** (v0.38.6.0): an invitation and a role change. `assertMayGrantRole()` in `memberService.ts` is the single implementation; `inviteMember` and `updateOrgMemberRole` both call it. The rule shipped with exactly one of its two enforcement points for months — `inviteMember` had it, `updateOrgMemberRole` did not — while `settings/team`'s `{isOwner && <SelectItem value="ADMIN">}` made it look enforced on both, so any ADMIN could promote any member by calling the mutation directly. **The client gate is an affordance; the service is the control.** Before adding a third path that assigns a role, check it goes through this helper. Verified by trace: the only other `OrganizationMember` writers are `orgService` (creates the founder as OWNER) and two activity-column updaters. Four rules that are easy to break: (1) **the acting role is resolved from the DATABASE, never a parameter.** `inviteMember` used to take an optional `actorRole` that failed OPEN when omitted, fed from `ctx.role` — which `createTRPCContext` sets to `null` on the impersonation branch before re-resolving. Same shape as the `email` parameters dropped in v0.34.0.0: while the parameter exists, every callsite is one wrong argument from restoring the hole. `actorId` is required for the same reason. (2) **`resolveActingRole` re-asserts the ADMIN floor, and that is not redundant with `adminProcedure`.** `adminProcedure` reads `ctx.role` once, when the request context was built; this reads the row as it stands. Without the floor the role costs a query but gates ADMIN *targets* only — `assertMayGrantRole` returns early below that tier — so a caller demoted mid-request could still flip members between STAFF and READONLY. Found by an adversarial pass, not by the checklist. (3) **The tier check runs BEFORE the target lookup**, so the rule is "an ADMIN may not submit `newRole: ADMIN`" independent of the target's current role. It costs one refusal where the no-op branch would have quietly succeeded; a test pins it. (4) **`removeOrgMember` is the one member mutation that does NOT re-check the caller** — pre-existing, tracked as a P2. It is not an exemption, just unfixed; do not cite it as precedent.
- Platform admin: `src/server/domain/platform-admin.ts` (`isPlatformAdmin()` with DB + env-var fallback)
- Advisory permission middleware: `src/server/trpc/advisory-permission-middleware.ts` (global, never blocks, logs mismatches)
- Company-scoped access: `requireCompanyAccess()` in `src/server/services/companyAccessService.ts` + the `companyScopedProcedure(opts?)` factory in `src/server/trpc/init.ts` (replaced the session-scoped `companyProcedure`/`companyAdminProcedure`/`companyPlanTierProcedure`, v0.29.2.0). Always reads `companyId` from tRPC input, never from session state — the session's "active" company can differ from the company named in the URL for a multi-company user, and authorizing off the session serves/mutates the wrong tenant. Use this factory for any new company-scoped procedure instead of reading `ctx.companyId`.
- Org↔volunteer access: `requireOrgVolunteerRelationship(orgId, userId, opts?)` in `src/server/services/orgVolunteerAccessService.ts`, backed by `findOrgVolunteerRelationship()` in `src/server/repositories/orgVolunteerRepo.ts` (v0.32.1.0). `staffProcedure` + `ctx.orgId` answer "is the caller staff, and at which org?" — neither says anything about a `userId` arriving in the procedure's **input**, and user ids are not secret (`/v/[userId]` is a public route). Any staff procedure that acts on an input-supplied `userId` must call this guard first. It accepts only relationships an org cannot mint unilaterally against a stranger — `APPLICATION`, `ORG_VOLUNTEER` (the roster row itself), `SHIFT_SIGNUP`, `ORG_MEMBER` — and deliberately excludes `VolunteerCredential`/`BackgroundCheckRequest` (circular: the write being authorized is the row that would authorize it), `VolunteerInvitation` (an outbound solicitation any staff user can create against any volunteer via the cross-org directory), and `OpportunityInterest` (a public marketplace heart-click). Throws `NOT_FOUND`, not `FORBIDDEN`, so "not yours" and "not real" are indistinguishable to a caller probing ids; `getOrgVolunteerRelationship()` is the non-throwing form for reads that render an empty state (`getOrgVisibleProfile` returns null). `acceptExistingCredential: true` is passed by `revokeCredential` and nowhere else — revocation is strictly narrowing so it cannot bootstrap itself, and without it a de-rostered volunteer's credential stays listed by `listOrgCredentials` but is permanently unrevokable. Gates `profile.getOrgVisibleProfile`, `credentials.issue`, `credentials.revoke`, and `backgroundChecks.initiate` — the last inside the shared Checkr/Sterling `initiateProviderCheck` path rather than per-caller, so it runs before the paid third-party call that receives SSN and date of birth. The returned kind is stamped onto audit metadata as `relationship`, so the authorizing edge survives a later roster soft-delete. Two things are deliberately NOT gated: `credentials.remove` (`removeCredential()` deletes on the `(userId, orgId, type)` compound key, so a stranger's row cannot match), and the FCRA resolution path `issueCredentialAndResolveFcra()`, which writes `CREDENTIAL_ISSUED` without a `relationship` key because it acts on an existing `BackgroundCheckRequest` that the guard already cleared at initiation — so audit rows from that path carry no `relationship`.
- Impersonation resolution: `resolveEffectiveUserId(realUserId, cookieValue)` in `src/server/lib/impersonation-context.ts` (v0.29.3.0) — pure function, no `getServerSession()`/`cookies()` inside it, so it resolves identically from tRPC's `createTRPCContext`, raw Route Handlers, and Server Component layout/page guards. Fails **closed**: returns `effectiveUserId: null` + `resolutionFailed: true` if a cookie was present but resolution threw — mutation paths and read-then-write SSR pages must check `resolutionFailed` and refuse rather than fall back to the real admin's identity (read-only nav/banner rendering via `getImpersonationContext()` may ignore it). Any new raw Route Handler or Server Component that reads `getServerSession()`'s `user.id` directly to scope a query/mutation must resolve through this helper instead, or it silently ignores impersonation like the bug this fixed.

Company-scoped mutations taken while impersonating (`company.switchCompany`, `linkNonprofit`, `unlinkNonprofit`, `invite` in `src/server/trpc/routers/company.ts` / `companyService.ts`) now stamp `impersonatedBy: ctx.realUserId` onto the audit log metadata so the real admin, not just the impersonated user, is attributable. - Application claiming: an orphan application (`submittedByUserId: null`) is **never** bound to a user implicitly. `screener.submit` is a `publicProcedure` accepting an arbitrary `submittedByEmail`, so orphan rows are attacker-controllable, and binding one mints an `APPLICATION` edge that `requireOrgVolunteerRelationship()` accepts as authorization for `profile.getOrgVisibleProfile` and `credentials.issue`. The predecessor `linkApplicationsToUser()` auto-bound every address match on each `/app/my-applications` load and was a live privilege escalation (fixed 2026-07-27). Binding now goes through `claimApplication()` in `my-applications.ts` → `claimApplicationForUser()` in `volunteer-applications.ts`, which enforces the email match **inside the Prisma `where` clause** — not a caller-side comparison — so a foreign application id matches zero rows. If you add another path that attaches an application to a user, it must go through this function or repeat its `where`.
- **Never use Prisma's `mode: 'insensitive'` on an authorization predicate.** It compiles to `ILIKE $1` with the value interpolated **unescaped**, so `_` and `%` become wildcards — and `_` is legal in an address `zod.email()` accepts. Verified in Postgres: `'jason.shultz@x' ILIKE 'jason_shultz@x'` is TRUE, so `j_smith@…` would match (and claim) `j.smith@…`'s row. This shipped briefly in the claim flow and was caught in review. Compare identities with plain equality against `normalizeEmail()`. Storage is kept canonical instead: T1's migration backfilled `VolunteerApplication.submittedByEmail`, and `screener.submit` normalizes on write via `.transform(normalizeEmail)`. Three regression tests in `applicationClaim.integration.test.ts` go red if `insensitive` is reintroduced.
- **`ctx.session.user.email` is NOT the effective user's address.** `createTRPCContext` builds the session as `{ ...realSession.user, id: effectiveUserId }` — under impersonation only `id` is swapped, so the email stays the *real admin's*. Any code pairing `session.user.id` with `session.user.email` is mixing two identities. - Roster convergence (E1a, v0.34.0.0): `ensureAppliedRosterRow()` in `src/server/services/appliedRosterService.ts` materializes the `OrgVolunteer` edge an approved application implies, called from **both** `updateOrgApplicationStatus()` (`screener-queries.ts`) and `claimApplication()` (`my-applications.ts`) inside their existing transactions. (2) The approval callsite gates on the **transition** (`previousStatus !== 'APPROVED'`), not on `status === 'APPROVED'`, because that mutation is not idempotent and gating on status alone resurrects a deliberately-removed volunteer (the soft-deleted row does not block a fresh insert). - Claimable-application decline (v0.34.0.0): `declinedByUserId`/`declinedAt` on `VolunteerApplication`, written only by `declineApplicationForUser()`, which enforces the email match **inside the `where`** exactly as the claim does. - Assign-to-shift (T8/T24, v0.35.0.0): `assignVolunteerToShift()` in `shiftSignupService.ts`, surfaced by `AssignVolunteerPicker` inside `ShiftDetailDialog`. - Volunteer revocation via `OrgVolunteerBlock` (v0.37.0.0): `leaveOrgRoster()` writes a block row in the same transaction as the soft delete, and `findOrgVolunteerRelationship()` suppresses every relationship kind except `ORG_MEMBER` and `EXISTING_CREDENTIAL` when one exists (both exemptions explained below — do not read the first clause alone). This exists because **every other edge in that guard is one staff can mint unilaterally** — `addVolunteer` takes an email address and needs no consent — so soft-deleting the roster row left the volunteer with no state the org could not recreate in two clicks. The rejected alternative (cancel the signups, filter `CANCELLED` out of the `SHIFT_SIGNUP` probe) fails for exactly that reason, and the pre-fix confirm copy admitted it: *"and they can add you again."* Four rules that are easy to break: (1) **`ORG_MEMBER` is exempt and the suppression path RE-PROBES for it** — a coordinator who is also on their own org's roster would otherwise lock themselves out of their own organization by leaving it, and only when they had also applied, since the probe short-circuits at `APPLICATION` and never reaches the member check. (2) **The block check runs AFTER the probes, not before** — blocks are rare, so checking first adds a query to every call to save one on almost none; the rejection path stays at four queries and the accept path pays one indexed lookup. (3) **Lifting is volunteer-initiated only**, via `liftOrgVolunteerBlock()` in `orgVolunteerAccessService.ts`, called from application submit (only when `submittedByUserId` is set — `screener.submit` is a `publicProcedure` and an attacker-supplied address must not clear a block), `claimApplication`, and `signUpForShift`. Adding an org-initiated lift would hand the revocation back to the party it protects against. In `claimApplication` it must run **before** `ensureAppliedRosterRow`, or the roster row is minted while the block still stands. (4) **`addVolunteer` refuses with FORBIDDEN, not the guard's NOT_FOUND** — that guard hides "not yours" behind "not real" because it takes a `userId` from input, but here the org already had this person on its roster, so there is nothing to conceal. Mutation-verified against real Postgres in `orgVolunteer.integration.test.ts`; note the `ORG_MEMBER` test there carries a deliberate `VolunteerApplication` so the probe cannot short-circuit past the block, or it would pass vacuously. **`EXISTING_CREDENTIAL` is exempt too** — suppressing it recreated the dead end `acceptExistingCredential` exists to prevent (a credential `listOrgCredentials` still shows but nobody can ever revoke), and revocation is strictly narrowing so a block has nothing to protect against there. **Count the two sets separately.** There are THREE roster-row CREATORS — `addVolunteer`, `ensureAppliedRosterRow`, `restoreVolunteer` — and FOUR paths that refuse while a block stands, the fourth being `assignVolunteerToShift`, which creates no roster row but ACTS on one. `restoreVolunteer` is the creator that does not look like a create and was missed until five review specialists caught it, because `restoreOrgVolunteer` matches any row with `deletedAt` set and nothing records WHO deleted it. A new-path rule phrased as "creates a roster row" would not catch the assign case; the rule is **creates OR acts on** one. **The concierge importer (T17, v0.38.0.0) is the first new path since, and it needed no new refusal** — precisely because it writes through `addVolunteer()` rather than reimplementing the insert, so it inherits the block check for free and reports the refusal per row. That is the pattern for any future bulk path: go through the service, do not repeat the guard.

- **Error disclosure is enforced on the SERVER; `safeErrorMessage` is the second half** (T37, v0.39.0.0). The allowlist lives once, in `src/server/domain/error-disclosure.ts` (`CLIENT_SAFE_ERROR_CODES`, `isClientSafeErrorCode()`, `GENERIC_ERROR_MESSAGE`), read by the `errorFormatter` in `server/trpc/init.ts`, by `query-error-card.tsx`, and by `server/trpc/error-reporting.ts`. **The entry above framed this as a client migration and that framing was wrong**: there was no `errorFormatter`, so the message had already crossed the network and was sitting in the browser's network tab and React Query's cache before any component chose what to render. A component can only decide what is *painted*. Eight rules, several of which were found only by an adversarial pass after the "obvious" version had already shipped in review: (1) **The code alone is NOT sufficient — the message must also be one WE authored.** `getTRPCErrorFromUnknown` resolves `message = opts.message ?? cause.message`, and tRPC manufactures `BAD_REQUEST` that way for *every* input-validation failure, so allowlisting the code alone shipped raw Prisma text under an allowlisted code. Verified by execution. The discriminator is `error.cause instanceof Error` — laundered — and a guard test (`error-disclosure.guard.test.ts`) bans a `TRPCError` literal carrying BOTH `message:` and `cause:`, because that idiom silently degrades hand-written copy to the generic string with no type error and no red test. (2) **`stack` is stripped on BOTH paths.** An allowlisted `FORBIDDEN` embeds the same absolute server paths as an internal error; the allowlist is a decision about the MESSAGE. Returning `shape` untouched on the allow path handed the stack back on every `pnpm dev` run. (3) **The formatter is NOT exempted in development.** `pnpm e2e` boots `pnpm dev`, so a dev exemption makes the control inert in the only automated environment that drives real HTTP. (4) **`onError` in `app/api/trpc/[trpc]/route.ts` is part of the fix, not garnish** — redaction removes the last place an unexpected failure was legible. It lives in `error-reporting.ts` rather than inline **because the route module is unreachable from a unit test**; a static assertion pins the wiring, since deleting the `onError:` line otherwise leaves the whole suite green while Sentry goes deaf. (5) **Disclosure-safe and fault are two different questions.** `SERVICE_UNAVAILABLE` is allowlisted for disclosure AND still reported — skipping it because it appeared in the allowlist turned a background-check provider outage into a silent one. Zod input failures are the inverse: skipped, because `screener.submit`/`leads.create`/marketplace/feedback are `publicProcedure` and `httpBatchLink` batches N calls, so reporting them let anyone with curl exhaust the Sentry quota. (6) **Throttle the noisy path, never the whole client.** A global Sentry `sampleRate` was tried and reverted: it is per-EVENT across the entire Node SDK, so it discards three quarters of a signal that fires once a year (`IMPERSONATION_RESOLVE_FAILED`, the audit-integrity `captureMessage`) as readily as three quarters of a flood. `withinReportBudget` bounds events per procedure+code per minute and leaves everything else at 100%; `console.error` is never throttled. `dedupeIntegration()` went with it — Sentry already GROUPS duplicates, whereas Dedupe DROPS them, so every "N occurrences" alert silently under-counted. (7) **A message a user is meant to READ needs an allowlisted code.** `throw new Error('Cannot remove yourself.')` maps to `INTERNAL_SERVER_ERROR` and now renders as generic copy — silently. **Eighteen** such refusals existed across `memberService` (11), `shiftService` (2), `shiftTemplateService` (2), `shiftSignupService` (2) and `employerReportService` (1) — count them off the diff, not off memory, which is how this shipped saying "fifteen" until a completion audit checked. **No message-based test can catch this**: `rejects.toThrow('Cannot remove yourself.')` passes identically for a plain `Error`, so assert the **code**. And auditing `throw new Error` is only half — an existing `TRPCError({ code: 'INTERNAL_SERVER_ERROR', message: … })` carrying user-facing copy is redacted by the new formatter, which is how `backgroundCheckService`'s "temporarily unavailable" nearly became a permanent-sounding failure. (8) **`safeCaughtErrorMessage()` for `mutateAsync` try/catch.** `TRPCClientError extends Error`, so `err instanceof Error ? err.message : fallback` — the idiom at every such site before T37 — passes and returns the raw message while looking careful. Corollary on the empty-state rule above: T37 found four more components with **no `isError` branch at all** (`CredentialWallet`, `NotificationPreferences`, `MarketplaceCard`, `TimezoneCard`), and none leaked anything — each rendered a *default*, which is worse than blank because it states something false: "No credentials yet" to a volunteer whose background check is verified, and "UTC (default)" for an org whose shift times are not in UTC. **`MarketplaceCard` and `TimezoneCard` read the SAME query**, so one failure rendered two stacked cards and announced two `role="alert"` regions until the branch was hoisted — check for a shared query before adding a per-card error branch.

- **A background check is DISCLOSED to its subject, and that email is the control** (v0.40.0.0). `backgroundChecks.initiate` is gated only by `requireOrgVolunteerRelationship`, which accepts `ORG_VOLUNTEER` — a roster row staff mint from an email address alone, sixty at a time via `pnpm import:roster`. So the platform could make a paid third-party call carrying someone's SSN and date of birth with no record they had agreed and **no way for them to find out**: the only background-check email went to org STAFF on a CONSIDER result, and the volunteer heard from us only on the FCRA pre-adverse path, i.e. only if the report came back badly AND the coordinator acted on it. Tiering `ORG_VOLUNTEER` out of the accepted set for this action was considered and **rejected** — the coordinator must already hold the SSN and DOB to submit the form, so an in-app edge adds no consent that is not already there, while blocking the concierge case outright (a spreadsheet of existing volunteers is entirely people who have never logged in). The subject is the only party who CAN detect an unauthorized check, so the fix is disclosure. Six rules, most of which were bugs first: (1) **The recipient is resolved from `userId` via `findEmailByUserId`, NEVER from `pii.email`** — that block is staff-supplied free text, so sending there hands the subject's only disclosure back to whoever is running the check. Same rule as `ctx.session.user.email` not being the effective user's address. Mutation-verified. (2) **`waitUntil`, not a bare `void`.** On Vercel the function can be frozen as soon as the tRPC response is written, so a floating promise races the freeze — and the thing dropped is the only disclosure the subject ever receives. `bulk-import-service.ts:98` already established this; the `.catch` stays INSIDE, because `waitUntil` keeps the instance alive but does not handle rejections. A test asserts `waitUntil` was called with a Promise, or "simplifying" it back to `void` is invisible to the whole suite and breaks in production only. (3) **`sendEmail` RETURNS `false` and never throws** — for a Resend error and for a bounce-suppressed address — so a `.catch` never fires on the likeliest failure. The boolean is read and a lost notice logs `DISCLOSURE NOT SENT` via `console.error`. **Two tests are needed, returns-false and rejects**: the rejection test passed while the returns-false hole stood. (4) **NOT `suppressUnclaimed`.** The guard is opt-in so the default is already right, but that is load-bearing rather than incidental: a volunteer typed in from a spreadsheet who has never logged in is exactly the person with the weakest consent and the strongest claim to be told. (5) **Guard 0 — the FCRA attestation — is refused in the SERVICE, not as `z.literal(true)` on the router**, because a Zod failure arrives as a tRPC-manufactured `BAD_REQUEST` whose message comes from the cause, which `errorFormatter` redacts to generic copy; the coordinator would be refused with no way to learn why. It runs BEFORE any query, so an unattested request never touches the volunteer's row. (6) **`consentAttestedBy` is evidence, so it is a plain `String` with no FK** (`AuditLog.actorId`'s `ON DELETE SET NULL` would empty it when the coordinator leaves — worthless in exactly the dispute it exists for), it is **not backfilled** (NULL means "we do not know", and inventing a value manufactures evidence about a real person's consent), and the audit row stamps `impersonatedBy` — `createTRPCContext` rewrites `session.user.id` to the impersonated target, so without it a platform admin can produce evidence falsely naming a coordinator as having sworn they hold a signed authorization. The gap this left — nothing bound the submitted `pii` to the `userId` — was closed by Guard 1.5 in the next entry.
- **The submitted PII must describe the volunteer being checked, and the email is the only field that can prove it** (T38, v0.41.0.0). `initiate` takes a `userId` AND a free-text `pii` block from the same form; until Guard 1.5 nothing checked they were the same person, so picking the wrong row sent a STRANGER's SSN and date of birth to a consumer reporting agency, filed the report against the intended volunteer, and stamped `consentAttestedBy` with a coordinator's name for a report about a different human. Guard 1.5 lives in `initiateProviderCheck` — the shared path, so both provider entry points inherit it, exactly as Guard 1 does. Five rules: (1) **The email is a CONFIRMATION field, not a payload field.** It must equal the account address (`normalizeEmail` on BOTH sides, plain equality — never `mode: 'insensitive'`), and what reaches the provider is the ACCOUNT's address regardless of what was typed. So the coordinator-controlled field can only confirm the identity, never steer the provider's correspondence. (2) **Deleting the field instead was considered and REJECTED** — it is strictly weaker. Deriving the address means the identity is never restated, so the wrong-row case proceeds in silence; requiring a match is what converts a row mistake into a refusal. This is the one place the "delete the parameter rather than validate it" rule (v0.34.0.0) does NOT apply, because here the redundancy IS the control. (3) **It runs AFTER `requireOrgVolunteerRelationship`, not before.** First, it answers "does user X have address Y?" for any `userId` a caller submits, and user ids are not secret (`/v/[userId]` is public). Behind Guard 1 the caller is already entitled to a record the roster shows them anyway. Pinned by a test asserting `findUserIdentity` was never called when Guard 1 rejects; mutation-verified by swapping the two. (4) **The name check WARNS, it does not refuse.** `submittedNameMatchesAccount()` (`domain/background-check.ts`) is token OVERLAP, not equality — legal names and account names legitimately differ (preferred names, marriage, a roster imported holding "Bob"), so a gate would block real checks on real people. A disjoint name stamps `identityNameMismatch: true` on the audit row, spread conditionally for the same reason as `impersonatedBy`. Its suffix filter is load-bearing: without it "John Smith Jr" and "Robert Jones Jr" overlap on `jr` and the mismatch goes unrecorded. (5) **`notifyVolunteerOfCheck` still re-reads the address rather than accepting the one the guard resolved** — an address parameter there is one wrong argument from being fed `pii.email` again. One extra indexed read on a path that just made a paid third-party HTTP call is not worth trading that for. **Two things this does NOT do, and both must stay said out loud.** (a) **SSN and DOB remain unverifiable** — the platform holds no copy, so a mistyped digit still reaches the provider. (b) **Against a HOSTILE coordinator the guard proves nothing**, because staff mint the shadow user from an address they type (`addVolunteer`, `pnpm import:roster`), so they can satisfy both sides of the equality themselves. It is a MISTAKE detector — it catches the coordinator who grabbed the wrong row — not an integrity proof. This is why nothing positive is stamped on the audit row: only `identityNameMismatch` on failure, never an "identity confirmed" key that a later reader would trust. Do not describe this flow as identity-verified.

- CSV: one parser and one writer, in `src/server/domain/csv.ts` (`parseCsvRecords`, `escapeCsvField`, `toCsvLine`). (2) **`FORMULA_LEAD` allows leading whitespace**, because Excel and Sheets trim before deciding a cell is a formula, so `\t=SUM(A1)` still executes. (3) **`unescapeCsvField` exists because our own export is an input to our own importer.** Without it a re-imported `+1 555 0100` persisted as `'+1 555 0100` — every international phone number — silently, since `volunteerPhoneSchema` accepts a leading apostrophe. An unterminated quote is now a `CsvFormatError` rather than swallowing the rest of the file into one field, which previously reported "0 valid, 1 invalid — Email is required" for a 60-row spreadsheet. `bulk-import-service.parseCsv` (the applications importer) still has its own naive parser; converting it is a separate open TODO.
- Responsive staff tables (T28, v0.38.1.0; carried to the other four by T36): `/app/volunteers` (`src/app/(app)/app/volunteers/page.tsx`) is the reference implementation for getting a data-dense staff table onto a phone. **All five staff tables now have it** — the roster plus `/app/applications`, `/app/opportunities`, `/app/shifts` and `/app/settings/team`. Five rules, every one of which was a bug before it was a rule: (1) **The table↔card switch is pure CSS.** Both trees render from the same array inside `hidden lg:block` / `lg:hidden` wrappers — never `useMediaQuery`. That hook (`src/lib/hooks/use-media-query.ts`) initialises to `false` and only reads `matchMedia` in an effect, so gating *layout* on it paints the mobile shape to every desktop user and swaps it after hydration; it is the same post-hydration flash the roster feature flag has no client read path in order to avoid. The cost is one hidden subtree in the DOM, and `display: none` removes it from the accessibility tree as well, so exactly one control per row is ever reachable. (2) **A modal is the one place `useMediaQuery` IS safe**, because nothing renders until the trigger is pressed and by then the effect has run — `AddVolunteerDialog.tsx` (Dialog above `lg`, vaul `Drawer` below), `feedback-widget.tsx`, `org-profile-form.tsx`. **Safe to read at OPEN, not to keep re-reading while open** (v0.38.2.0): `Dialog` and `Drawer` are different root elements, so a live value that crosses the breakpoint mid-session unmounts one subtree and mounts the other, taking the form and everything typed into it. That is an ordinary gesture — an iPad rotating portrait→landscape crosses 1024 (834 → 1194), as does snapping a desktop window — and `useMediaQuery` subscribes to `change`, so it fires every time. A modal holding one throwaway field can live with it; `AddVolunteerDialog` accumulates a batch, so it FREEZES the shell while `open` is true and re-reads it while closed. **That freeze is now `useFrozenDesktopShell(open, query?)` (`src/lib/hooks/use-frozen-desktop-shell.ts`), extracted at T27's fourth Dialog/Drawer switch — do not re-inline it, and do not call `useMediaQuery` directly in a new modal.** It defaults to `DESKTOP_QUERY` (`lg`) and takes an override, so an `md` modal can comply rather than being forced back to a hand-rolled freeze. Extracting it also changed what is testable: the *visual* consequence (which shell paints) is still unreachable in jsdom, but the *resolution rule* is a pure function of `open` and the live query and now has tests including the iPad-rotation case, so the old "held by a comment, not a test" caveat applies only to the former. See the "Stay-open add-volunteer form" entry below. **One page still violates this**: `admin/feedback/page.tsx:91-92` gates its whole list/detail split on `isDesktop`/`isTablet`, so a platform admin on a desktop gets the mobile single-column tree painted first and swapped after hydration. Fix it the same way the roster does when that page is next touched; it is a platform-admin surface, which is why it has gone unnoticed. Match the **page's** breakpoint rather than the sibling component's: `AddVolunteerDialog` uses `lg` where the other two use `md`, because a 768–1023px band where the list behind the modal is already cards but the form is still a centred dialog is a worse inconsistency than differing from a sibling. Nothing enforces the two halves agreeing (one is a Tailwind class, the other a media-query string) — P3 in `docs/TODOS.md`. (3) **`Card`'s base styles fight `divide-y`.** It is `flex flex-col gap-6 … py-6`, so each hairline draws on a row's top edge while the 24px gap holds the rows apart and the rule floats in open space instead of separating anything. Use `CardList` (`src/components/app/card-list.tsx`), which is `Card` plus the `CARD_LIST` string `gap-0 divide-y py-0`; extracted at its fifth copy by T36, so do not re-inline it. **`ShiftsClient` deliberately uses neither** — its list already sits inside the page's "Shift Schedule" `Card`, so a second one is double chrome, and it renders a plain `divide-y` wrapper instead. Cancelling the inherited `px-6` with `-mx-6` was tried and reverted: it makes the list wider than the wrapper the e2e measures and fails as internal sideways scroll, which is the exact failure these lists exist to remove. `admin/platform/users/page.tsx` still ships the un-neutralised idiom. (4) **Visibility belongs on a wrapper `div`, never on the `Card` itself.** `hidden` and Card's own `flex` are both display utilities, so tailwind-merge drops one of them and which survives is a detail of the merge rather than of this file — a `lg:block` that appeared to work would have silently disabled Card's flex column. (5) **Duplicating a row duplicates its accessible name too.** Each `Remove` carries `aria-label="Remove {name} from your roster"` (a rotor otherwise lists N identical "Remove" buttons), removals and undos are announced through one discrete `<output aria-live="polite" class="sr-only">` message rather than by wrapping the list — the list also changes on search and on Load more, and announcing the whole roster per keystroke is worse than announcing nothing — and only the row being mutated goes `disabled` — via **`usePendingIds()`** (`src/lib/hooks/use-pending-ids.ts`), never a bare `isPending` and **never `mutation.variables` either**. That second half is a correction: `variables` was the documented rule until T36's adversarial review checked it against query-core, where `MutationObserver.mutate()` calls `this.#currentMutation?.removeObserver(this)` before starting the next call — so `variables` and `isPending` describe only the MOST RECENT mutation. Act on row B while row A is in flight and A's controls silently re-enable, so at most one row is ever disabled however many requests are open. On `/app/opportunities` and `/app/settings/team` that was strictly WORSE than the bare `isPending` it replaced, which at least made concurrent submits impossible: the concrete failure is two `members.updateRole` writes for one member on separate requests with no ordering guarantee, landing the role from the first click while the coordinator watched the second succeed. `usePendingIds` keeps a `Set` fed from `onMutate`/`onSettled` (settled, not success — releasing only on success leaves a failed row disabled forever), so several rows can be busy at once and each releases on its own request. It is keyed by ROW, not by mutation, because "is this row busy" is one question even where three mutations act on it (shifts). **Four of the five staff lists use it — `/app/applications` does not, because it has no row mutations at all** (its rows only navigate). Do not "make it consistent" by adding it there; the hook has no rows to hold. Corollary for tests: with both trees mounted, every name, address and badge matches TWICE, so `page.test.tsx` scopes through `within(getByTestId('roster-table'))`; jsdom has no layout, so a CSS breakpoint switch cannot be tested there at all and the 375px e2e is the only thing that proves which tree a human sees (`e2e/staff-created-volunteers.spec.ts` for the roster, `e2e/staff-tables-mobile.spec.ts` for the other four). (6) **The row is only the whole tap target when the detail view actually HAS the row's actions.** T28 could move `Remove` into a dialog because T27 had just built one holding it; T36 found the opposite on three of four pages — `Publish`/`Close` exist on the opportunities LIST and nowhere else (the detail page has only `Edit`), `Complete`/`Cancel`/`Delete` exist on the shifts list and nowhere else, and the team page has no detail view at all. Those three keep their actions on the card, so the card is a `<div>` with a linked title rather than a `<button>` — which is also the only valid markup, since a nested `<button>` inside a tappable row is not. **Check the destination before deciding a card can drop a control**, or the layout change quietly becomes a capability change. (7) **Overflow is asserted at `documentElement` level**, through `expectNoHorizontalOverflow`/`expectNoInternalScroll` in `e2e/utils/layout.ts`. These were region-scoped until the app-shell top bar was fixed alongside T36 — it overflowed on every authenticated page, so a page-level assertion failed on shared chrome and said nothing about the page under test. The two are different properties and both are needed: a `Table`'s own `overflow-auto` wrapper scrolls internally while the document stays exactly the viewport width, so the document check cannot see it. The **768-1023px band is the load-bearing viewport**, not 375px — the shell was 126px over at 800px against 22px at 375px, because the wordmark and both switchers render there beside a toggle that is still `lg:hidden`. Anyone checking a chrome fix on a phone alone will call it a rounding error. **And a document-level check is necessary but not sufficient**: content can break its container and still land inside the viewport. `/app/opportunities`' header actions ran 32px past the page padding and stopped at exactly 375, so every overflow assertion passed while the button sat flush against the screen edge — it was caught by screenshotting the page, not by a test. Where a container's bounds are the requirement, assert against the container, and measure the widest DESCENDANT rather than the wrapper (the wrapper stays in bounds while something inside it does not). (8) **Mutation-test a layout assertion before believing it.** Three of the four written for T36 were vacuous on the first attempt: the header geometry check measured the wrong node; the e2e fixture strings were hyphenated, and a hyphen is a line-break opportunity (UAX #14 class BA), so deleting `truncate` would have wrapped harmlessly and stayed green — use underscores, which are not; and a sonner width-cap assertion passed with the cap removed, which is how the cap was discovered to be **inert** and dropped rather than shipped. `docs/TODOS.md`'s claim that the toaster was a second overflow offender is wrong and is corrected in `sonner.tsx`: the 391px figure is the zero-height `position: fixed` `<ol>`, and sonner already clamps the toast `<li>` to the viewport
- Stay-open add-volunteer form (T25, v0.38.2.0): the add form on `/app/volunteers` no longer closes on a successful add — the fields clear, focus returns to Name, an `<output>` running count appears above the footer, and the footer flips `Cancel`/`Add volunteer` → `Done`/`Add another`. The task is a coordinator typing a sign-up sheet, so the whole design goal is that the next name is reachable without the mouse. Five rules, each of which was a bug before it was a rule: (1) **The page owns `open` and there is exactly ONE dialog.** The empty state used to mount its own `AddVolunteerDialog`, and it lives inside `page.tsx`'s `volunteers.length === 0` branch — so the first successful add flips that branch and unmounts the form the coordinator is still typing into, which is exactly the batch-entry case the feature exists for. Harmless while the form closed on success, and invisible to the unit tests, which render the component directly and never through the page. The empty state now renders the shared `AddVolunteerButton` and calls the page's `handleAddOpenChange`. That button guarantees the **affordance only** — it is not a Radix `DialogTrigger`, so Radix never registers it as the focus-return node (P3 in `docs/TODOS.md`) — and **any future surface that wants an add form must open the page's instance rather than mount a second one**, since two mounts means two running counts that disagree (P3). (2) **The shell is frozen across `lg` while the form is open** — see rule (2) of the responsive-tables entry above. The freeze now lives in `useFrozenDesktopShell` and has its own tests; what remains untestable is which shell actually paints. Do not "simplify" it back to a bare `useMediaQuery` read. (3) **The SECONDARY button is disabled mid-flight too, not just submit.** Closing unmounts the form and with it the mutation's `onSuccess`, so a volunteer the server DID create gets no toast, no place in the count and — the part that outlives the moment — no `onAdded()`, leaving the roster behind the form permanently missing them with nothing to suggest it is wrong. `Add another` → `Done` in one motion is how a batch naturally ends, so this is the likely path, not a race. Escape and the overlay still close mid-flight and still orphan the callback (P3, deliberately: trapping someone in a modal because a request is slow is the worse failure; the durable fix is hoisting the mutation to `page.tsx`). (4) **The `aria-live` count region mounts EMPTY with the dialog and reserves its line (`min-h-5`).** Only its content is conditional: a live region inserted into the DOM in the same commit as its first text is unreliably announced, so the first add — the one that tells the coordinator the form works at all — is the one most likely to be silent, and `hidden`/`empty:hidden` restores that bug because `display: none` takes it back out of the accessibility tree. The reserved line is not cosmetic either: `DrawerContent` is pinned to the bottom, so a region that grows on first add pushes the sheet UPWARD and moves the Name input out from under the caret at the exact moment focus was returned to it. The same region doubles as the in-flight status (`Adding…`), because the disabled secondary is otherwise the silent one. (5) **The batch result has to outlive the dialog.** Toasts have long expired on a twenty-name batch and the count unmounts with the form, while the list behind it is still filtered — `refresh()` deliberately keeps `search` — so "3 added" can be followed immediately by "No volunteers match that search." `page.tsx` publishes a batch notice on close and offers `Clear search to see them` when a filter is active. Two shell details that came out of the same ship: `DrawerContent` is `max-h-[85vh] flex flex-col` and `drawer.tsx` declares no overflow utility anywhere, so the body wrapper carries `overflow-y-auto min-h-0` — **`min-h-0` is not optional**, a flex child will not shrink below its content without it and `overflow-y-auto` alone does nothing; and both footer buttons are min-width-pinned to their longest label, since a right-justified row whose labels change on every submit moves the button being pressed twenty times in a row. Corollary for tests: **a one-add e2e is not coverage of a stay-open form.** `addVolunteersViaUi(page, entries[])` types a second name into a form that has just survived the empty→populated flip, and names the submit per iteration (`Add volunteer`, then `Add another`), so a form that closed on success fails on the second pass with nothing to click.
- Volunteer detail dialog (T27, v0.38.3.0): clicking a roster row opens one page-owned `VolunteerDetailDialog` showing that volunteer's org-scoped facts — email, phone, when and why they were added, account state, attended-shift history and hours. Rules worth keeping, most of which were bugs first: (1) **The shift history is org-scoped through `shift: { orgId }`, and the filter is SHARED with the count beside it.** `ShiftSignup` has no `orgId` column, so the join is the only way to express it. `listAttendedShiftsForUserInOrg` and `countAttendedShiftsByUser` both go through one private `attendedShiftWhere(orgId, user)` in `orgVolunteerRepo.ts`, which returns the COMPLETE `where` and takes the user predicate as an argument — deliberately not a fragment to spread, because `{ ...filter(orgId), shift: {…} }` compiles, typechecks and silently drops the org join — the dialog IS the drill-down of the roster row's `Shifts` cell, so two hand-written copies would let them disagree and the symptom is a row reading 12 opening a dialog showing 9. **`getAttendedShiftsForUser` in `shiftSignupRepo.ts` is cross-org ON PURPOSE** (a volunteer's own lifetime hours, platform tenure badges) and must never be reused by a staff surface; the design doc specified T27 against it, which would have shown org A every shift a shared volunteer worked for org B. Mutation-verified: dropping the join turns two `SECURITY:` integration tests red. (2) **The READ is uncapped, the WIRE is capped at `SHIFT_HISTORY_WIRE_CAP` (50), and the totals are computed BEFORE the slice.** Both halves are load-bearing and it is easy to get exactly one right. Capping the read under-reports the total and the `N attended` figure, which sit under a cell showing the uncapped count. Capping nothing ships O(tenure): ~1800 rows / ~420KB for a daily volunteer over five years, to paint fifty. The service sums across everything, sends 50 plus a `shiftCount`, and the dialog renders "showing N of M" off the count rather than off `shifts.length`. The cap lives in `domain/org-volunteer.ts` because both layers need it — as a client-only constant the server had no ceiling available to it even in principle. (3) **Hours round ONCE from the raw millisecond sum** (`sumAttendedHours` in `domain/shift.ts`), never by adding rounded per-row figures: three 20-minute shifts are 1h, not 0.9h, and a test pins exactly that. One decimal, matching `orgAnalyticsRepo`'s org-facing convention rather than `volunteerIdentityService`'s whole hours — a 2.5h Saturday shown as "3h" is a visible lie on a list short enough to check by hand. (4) **ONE dialog, page-owned, with NO `DialogTrigger`.** Both roster trees are always in the DOM (the switch is pure CSS), and Radix's trigger model needs trigger and content as siblings under one `<Dialog>`, which two trees of rows cannot be. Two consequences that each cost a round: Radix restores focus to `<body>` on close, so the restore must happen in **`onCloseAutoFocus` with `preventDefault`** — an `onOpenChange` handler runs FIRST and is silently overwritten; and the node to restore to is not always the clicked one, because a clickable `<tr>` cannot hold focus and because a click on the name button bubbles to the row, whose handler then overwrites the button with the `<tr>`. Rows hand over their `[data-row-trigger]` instead. **Any future shared-dialog-from-a-list inherits both.** (5) **The dialog fetches its own data**, which is what makes an open dialog immune to the list underneath it — search, `Load more` and the invalidate after an unrelated removal can all drop that row and none of the FACTS move. The clicked row's `displayName` is a first-paint fallback only and is superseded by the query's own copy the moment it lands; reading the prop unconditionally was wrong in a way the docstring denied, since it is evaluated on every render and flipped the title to "Volunteer" (and the Remove label to "Remove Volunteer from your roster") under an open dialog when the row left the list. (6) **It owns no mutation**: Remove calls the page's, so one Undo toast and one `removedNames` map serve both surfaces, and closing mid-flight cannot orphan the callback — the P3 `AddVolunteerDialog` carries precisely because its mutation is declared inside the unmounting component. Close-on-success gates on `id === variables.volunteerId`, not unconditionally. (7) **`Remove` left the mobile card**, closing T28's tracked deviation — and not merely for mis-tap reasons: once the row is a `<button>`, a nested `<button>` is invalid markup, so "row is the tap target" and "Remove moves into the dialog" are one decision. Desktop keeps its inline Remove with `stopPropagation`, so removing someone does not also open them on the way out. (8) **Copy on this surface is STAFF-voiced** — `ORG_VOLUNTEER_SOURCE_COPY_STAFF`, not the `ORG_VOLUNTEER_SOURCE_COPY` whose docstring says it is "told to the volunteer themselves". Rendering the volunteer's Record here showed the coordinator "Added when they approved your application", inverting who approved whom. **Share the ENUM, never pronoun-bearing prose** — exhaustiveness is what a `Record` over the enum buys; voice is per-audience and does not transfer. `roster-export.ts` still ships the volunteer voice into the staff CSV (pre-existing, P2). (9) **`QueryErrorCard` is deliberately NOT used inside the dialog** — it is a `Card`, and a bordered card inside an already-bordered dialog is double chrome — but `safeErrorMessage` still is, because the never-render-`error.message`-raw rule is about the message, not the container. The branch order is still loading → error → content, pinned by a test asserting the empty-state copy is ABSENT on error: without the error branch this falls through to "No shifts recorded here yet", which reads as a fact about the volunteer rather than a failure.
- Raw SQL: never compose `Prisma.sql` fragments (via `Prisma.join`, conditional `Prisma.sql`/`Prisma.empty`) and interpolate them into `$queryRaw` templates. Turbopack dev duplicates the generated client's `Sql` class across module graphs, `instanceof` fails, and the fragment is sent to Postgres as one literal parameter ("invalid input syntax" 500s that only reproduce under `next dev`). Write one static template with NULL-checked optional filters instead — prefer the sargable form `col >= COALESCE(${x}::timestamp, '-infinity'::timestamp)` for range filters (index-friendly under generic plans), or `(${x}::type IS NULL OR col = ${x}::type)` for types without ±infinity (booleans etc.).
- No Prisma calls in tRPC routers. Routers call services. Services call repositories. Period.
- All DB writes go through services (so audit logging is automatic).
- Every table gets createdAt, updatedAt, and if relevant deletedAt. Soft delete now saves you.
- Zod schemas live next to domain models and get imported on both sides. No duplicating.
